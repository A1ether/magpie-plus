## 1. 问题现象

**结论：CodeArts 华为云卡片「今日用量」显示为 0（实测值是 **0.01** CREDITS，被当成 0），而同一张卡片的余额当天已下降 135.68。**

| 观测项 | 值 | 来源 |
| --- | --- | --- |
| 卡片余额（AK/SK 账户级口径 `usageTotalPackageCredit.package_credit_remain`） | 31525.53 → 31389.85（10-25 00:02 → 01:31） | 本地采样 `.run/usage-history.json`（key `codearts#CodeArts 华为云 · a1ether`）；末值与 `/api/summary` 实测一致 |
| 当天观测到的下降合计（= 用户确认的「用量」口径：该日额度减少量之和） | **135.68** CREDITS | 同上（12 个样本，逐段下降之和） |
| 卡片「今日用量」实测值 | **0.01**，`sources.todayUsed: "upstream"` | 本机 `/api/summary`（2026-10-25 01:31） |
| 上游「按天」明细给出的今天 | **0.01** CREDITS | 同上（来源标为 `upstream`，即控制台按天图表） |
| 上游「按天」明细给出的昨天（10-24） | **1821.95** CREDITS | 同上 |

**第二组不一致（需要用户对照华为云页面裁决）**：上游说 10-24 用了 1821.95 积分，而 10-24 全天余额**一动没动**（本地采样 01:53 → 23:42 恒为 29525.53，其间只有一次 +1000 签到变成 30525.53，没有任何下降）。即上游「按天用量」与「余额扣减」并非同一本账。

触发环境：单账号 `codearts` 卡片（Cookie 走控制台逐笔 + AK/SK 走余额），服务以 `node dist/server.js` 长驻（`.run/server.log`）。

影响范围：**直接受影响的是「今日用量」**；「昨日用量」的正确性取决于上一段那个待裁决问题（当前取上游值）；余额、积分批次、到期时间线不受影响。用户明确要求「今日用量要反映真实的当天消耗」，因此这是取数口径缺陷而非展示问题。

## 2. 根因分析

**结论：CodeArts 控制台的「按天用量」不是余额扣减的逐笔账，而是**统计模型给出的总量**（用户 2026-10-25 指出：该页「使用明细」不能按笔获取）。它对**正在进行中的今天**明显滞后 —— 实测今天只给到 0.01，于是卡片显示 ≈0，而余额当天已下降 135.68；而编排层在「上游覆盖」时无条件信任这个值（缺记录还用 `?? 0` 补 0），把本地实时观测完全丢弃了。**

口径链路（逐行证据）：

1. 适配器声明覆盖：`src/providers/codearts.ts:585-624` —— 只要按天图表响应里能找到 `name` 含 `credit` 的 series 且其 `cells` 是数组，就置 `useCovered = true`（`codearts.ts:616`）。当时**不检查「今天」这一格的值是否可信**（v3.1 已补诊断，见第 3 节第 5 条）。
2. 缺记录补 0：`src/usage-ledger.ts:92-95` —— 覆盖维度用 `??= 0` 把缺记录补成 0。这条口径对**已结束的日子**成立（有完整记录集，0 是确定值），对**尚在进行中的当天**不成立。
3. 上游覆盖即无条件用上游：修复前的 `src/service.ts` 是 `todayUsed: usedUpstream ? summary.usedToday ?? 0 : local.todayUsed`。当上游今天给的是滞后的 0.01 时，卡片就显示 0.01，本地观测到的 135.68 被丢弃（现由 `src/service.ts:146-168` 的 `reconcileToday()` 取代）。

实测证据（本机 `/api/summary` + 本地采样，均只读）：

| # | 事实 | 证据 |
| --- | --- | --- |
| 1 | 卡片的值确实来自上游、且等于上游那个 0.01 | `/api/summary` 实测 `dailyUsage.todayUsed = 0.01` 且 `sources.todayUsed = "upstream"` |
| 2 | 上游今天 0.01 ≪ 余额当天下降 135.68 | 本地采样 `codearts#…a1ether`：00:02:52 `31525.53` → 01:31:37 `31389.85`，逐段下降之和 135.68 |
| 3 | 上游「按天用量」与余额扣减**不是同一本账** | 上游说 10-24 用了 1821.95，而 10-24 的余额全程无下降（`29525.53` → 一次 +1000 签到 → `30525.53`） |
| 4 | 不是「接口挂了 / 解析失败」 | 若失败、空响应或找不到积分序列会打印 `codearts.ts:578`、`589`、`620` 的诊断行；`.run/server.log` 里只有「活动逐笔」正常日志，没有任何诊断行 |
| 5 | 本地采样采的正是卡片余额本身，因此它与「用量 = 余额减少量」的口径严格一致 | `src/service.ts:357`（`usage.observe(key, displayedAmount(snapshot))`）、`src/service.ts:140-144` |

另一条同处代码的静默风险（v3 已一并修掉）：若上游把 `xLabel` 换成非 `YYYY-MM-DD` 的格式（如 `2026/10/25`），**所有**格都会被丢弃，而覆盖声明仍是 `true` —— 表现为「今日与昨日用量都是 0」（`localNoonOf` 的解析规则见 `src/usage-ledger.ts:59-64`）。

为什么不改用别的上游源（已排查，否决）：

| 备选 | 结论 |
| --- | --- |
| 费用中心抵扣明细 `ListFreeResourcesUsageRecords`（含 `deduct_time`/`used_amount`，理论上是日级用量的权威源） | 该账号在费用中心没有任何资源包、`/billing/` 一律重定向（agency 上下文），BSS 路径已被实测否决 —— 见 `docs/fixes/CodeArts-华为云登录态频繁失效-修复方案.md` §3.3「Phase 0 第二轮」 |
| 控制台逐笔 `credit/admin/usage` | 本账号窗口内 0 条、字段待确认（主用按天 charts 的原因见 `docs/plans/供应商卡片-用量与增量字段-开发设计方案.md:150`） |
| 控制台「使用明细」页的按天统计（现用源） | 用户确认**不能按笔获取、是统计模型的总量**；实测当天严重滞后（0.01 vs 135.68）且与余额扣减不同账 —— 只能作为**已结束日子**的参考，不能作为当天的真值 |

**待用户裁决（不影响本修复的可用性）**：上游按天数字与余额扣减为何不同账（统计口径差异 / 结算滞后 / 计费对象不同）。本修复对此不做假设：**今日取两个观测的较大值**（不会把滞后的 0.01 当真值），**昨日仍以上游为准**（它是完整记录集，且用户当前看到的 1821.95 与华为云页面同源）。若用户对照页面后认为「用量必须严格等于余额减少量」，则改为备选方案 A（见第 3 节）。

## 3. 修复方案

**结论（v3.1）：日级字段按「日」判定来源 —— 已结束的日子（昨日）以上游明细为准（缺记录 = 0）；进行中的当天（今日）取「上游值 vs 本地实时观测」的**较大值**；来源逐字段如实标注。**

改动点清单：

| # | 文件 | 改动 | 理由 |
| --- | --- | --- | --- |
| 1 | `src/service.ts` | 新增 `reconcileToday()`（`src/service.ts:146-168`）：今日取「上游 vs 本地观测」较大值（本地无样本 → 上游；上游更大 → 上游且来源 `upstream`；本地更大 → 本地且来源 `mixed`）；无上游覆盖 → 本地 | 上游按天统计当天滞后（实测 0.01 vs 135.68），本地观测会漏（服务没开），取大不双计也不低估 |
| 2 | `src/types.ts` | `DailyUsage.sources` 由「按维度（`used`/`added`）」改为「按字段（四个键）」 | 同一天里「今日」可能来自本地观测、「昨日」来自平台明细，按维度无法如实表达 |
| 3 | `src/aggregate.ts` | 合并卡片的 `sources` 归并改为逐字段 | 与 2 同步（`mergeSources` 语义不变） |
| 4 | `public/app.js` | 四字段 tooltip 取各自来源键；来源文案去掉「该平台无此明细」这类不再总是成立的措辞 | 与 2 同步 |
| 5 | `src/providers/codearts.ts` | ① `cells` 存在但一格都解析不出 → **不声明覆盖**（回退本地兜底）+ 诊断日志；② 没有积分序列 → 诊断日志（原先完全静默）；③ 没有「今天」这一格 → 诊断日志。三种诊断在同一进程内**只在结论变化时打印一次**，避免 5 分钟一轮刷屏 | 修掉第 2 节的次生静默风险，并把「上游今天有没有出数」变成可观测事实 |
| 6 | `src/cli/codearts-console-probe.ts` | 新增按天图表接口的原始响应打印（脱敏） | 让第 2 节「待确认」项下一次就能坐实 |

关键实现（`src/service.ts`）：

```ts
function reconcileToday(
  upstream: number | undefined,
  local: number | null,
  covered: boolean,
): { value: number | null; source: UsageSource } {
  if (!covered) return { value: local, source: 'local' };
  const value = upstream ?? 0;
  if (local === null || local <= value) return { value, source: 'upstream' };
  return { value: local, source: 'mixed' }; // 本地观测到得更多（上游当天滞后/缺格）
}
```

备选方案（**A：用量一律以余额观测为准**，即用户提出的「换一种处理方式」的严格版本）：

| 方案 | 口径 | 代价 |
| --- | --- | --- |
| **A（备选，未实施）**：`用量` 两维全部改为本地观测，`CodeArts` 不再声明 `covers.use` | 与「用量 = 该日额度减少量之和」严格一致：余额动了多少就是多少（10-24 会显示 0，因为当天余额确实没动） | 服务没跑的那天没有样本 → 昨日/今日都显示「–」；丢掉上游对已结束日子的完整记录；与用户当前在华为云页面上看到的 1821.95 不一致，需要用户先确认真实口径 |
| **B（本修复采用）**：今日取较大值、昨日以上游为准 | 今天立刻反映真实消耗（135.68），昨日保持与页面同源的数字 | 两个来源口径不同账时，同一天的「今日/昨日」可能来自不同账本（来源标注会区分） |
| C：一律上游优先（本次初版实现） | — | 已被实测证伪：上游今天给的是滞后的 0.01，`> 0` 判断根本不成立 |

> 选 B 不选 A 的理由：A 会让**已结束的日子**也回退到只剩余额的观测记录，服务停机的那几天直接变成「–」；而 B 只是把「当天尚未结算」这一段时间交给实时观测，对历史日仍保留上游的完整记录。若用户对照华为云页面认定「用量就必须等于余额减少量」，改用 A 即可（把 `covers.use` 从 CodeArts 适配器去掉即可，改动量 1 行 + 文档）。

对现有逻辑的影响（逐条）：

| 影响面 | 说明 |
| --- | --- |
| Qoder / Trae / CodeBuddy / MiniMax | 逐笔明细源、当天实时出数，通常 ≥ 本地观测（两者同源同量级）→ 取较大值等价于「谁更全用谁」，行为基本不变；上游滞后时由本地纠偏 |
| 昨日及更早 | 规则不变：覆盖维度用上游（缺记录 = 0），未覆盖回退本地采样 |
| A1etherOpenAi（无明细接口） | 不变，四字段仍全部本地采样，来源 `local` |
| 聚合层 | `totals` 数值不变；只有 `dailyUsage.sources` 的键变了 |
| 缓存 / 上游压力 | 无变化（不新增请求） |

## 5. 风险与回滚

| 风险 | 说明 / 处置 |
| --- | --- |
| 已修：上游当天滞后给「非 0 的小值」 | 实测 0.01 —— 初版「上游 > 0 就用上游」的判断被证伪；v3.1 改为取较大值后已消除 |
| 已知边界 1：批次过期会被计入今日用量 | 本地观测的口径是「余额下降量」，而积分批次过期同样会让余额下降（控制台按天统计不含过期）。今日改为取较大值后，过期日的本地观测会被采纳 → 用量虚高。识别方法：tooltip 来源为 `mixed` 且数值明显大于平台页面；处置：若真出现，引入「按批次到期剔除」（需适配器提供当日过期额，属新需求） |
| 已知边界 2：两个来源口径不同账（待裁决） | 实测 10-24 上游 1821.95 而余额零下降。当前实现：昨日以上游为准、今日取较大值 → **同一天内今日/昨日可能来自不同账本**（来源标注会区分）。若用户裁决为「必须与余额一致」，改用第 3 节备选 A |
| 已知边界 3：服务当天没被打开过 | 本地无样本 → 今日用量回退上游值（可能仍滞后）；这是项目既有的「本地采样依赖服务在线」限制（见 `docs/modules/项目整体-代码Wiki.md` 的同名风险行），不是本次新增 |
| 契约变更 | `dailyUsage.sources` 的键从 `used/added` 变为四字段名；前端与后端同仓库同批部署，无外部消费方（`/api/summary` 只在看板内使用） |
| 回滚 | 纯逻辑替换 + 契约改名，`git revert` 本次提交即可；也可只把 `reconcileToday` 的调用换回旧三元表达式（前端对缺失的 `sources` 键有 `?? local` 兜底，能容忍旧后端） |
