# 更新与发布流程

> 2026-10-28 · 适用于 `main` 分支（magpie plus / 余额看板 fork）
> 结构说明见 [FORK.md](../FORK.md)；跑起来看什么见 [本地启动与验收](本地启动与验收.md)。

四步，顺序不要颠倒：

```
取两个上游最新 → 构建 → 本地网页端预览、确认 → 才构建桌面 App
```

**桌面 App 永远放在最后**：网页端是同一份 GUI 代码（`internal/gui/assets`）和同一个网关，
预览确认过的东西才值得打进 `magpie plus.app`。改一行代码就出一次 App 是浪费，而且装进
`/Applications` 之后不容易分辨是哪个版本。

---

## 0. 两个来源，源码都在本仓库

| 来源 | 远程 | 在本仓库的形态 | 更新方式 |
|---|---|---|---|
| magpie（载体、GUI、网关） | `upstream` = `yetone/magpie` | 本仓库自身就是它的 fork；它的每个分支与 tag 另归档在 `vendor/upstream/*`（FORK.md §14，每日 workflow 自动追） | `git merge upstream/main` |
| power-meter（余额看板 sidecar） | `power-meter` = `A1ether/power-meter` | `third_party/power-meter/`（git subtree，95 个文件；`node_modules`、`dist`、`.env`、`accounts.json` 不入库） | `git subtree pull` |

两边源码都在本仓库，所以**克隆一份 `A1ether/magpie-plus` 就够构建**，
不依赖 `~/DevSpace/power-meter` 这份外部 checkout，也不依赖上游是否还在线。

## 1. 取上游最新

```bash
cd ~/DevSpace/magpie+powermeter
git switch main
make update
```

`make update` 做三件事，工作树不干净时直接拒绝：

```bash
git subtree pull --prefix third_party/power-meter power-meter main --squash
git merge upstream/main
```

要单独做、或想看每一步的输出：

```bash
make update-power-meter     # 只跟 power-meter
make update-upstream        # 只跟 magpie 上游
git log --oneline main..upstream/main | wc -l    # 还差多少提交
```

**冲突**：两个 `git` 命令遇到冲突都会停下（不会自动提交），退出码非 0。
冲突面基本固定在这几处，两侧的改动通常都是「各加各的」：

| 文件 | 两边各加了什么 |
|---|---|
| `internal/gui/assets/index.html` | fork 的 `<script src="plugins/powermeter/page.js">` 与上游新增的 script |
| `internal/settings/settings.go`、`internal/gui/api.go`、`internal/gui/settings_keep_test.go` | fork 的 `PowerMeter` 与上游新增的设置项 |
| `internal/gateway/routing.go`、`trace.go`、`internal/routes/routes.go` | fork 的 `Expires`/`ExpiryFirst` 与上游新增的 seat 字段 |
| `docs/subsystems/gateway-routing.md` | 同一行表格：保留上游整行，再把 fork 的 `expiry` 段插回去 |
| `Makefile`、`.gitignore` | 行级的并列增删，两边都留 |

解冲突的规矩：**上游的改法为准，fork 的二开原样保回来**；不要为了少冲突把二开删掉。
解完先编译再提交：

```bash
gofmt -l $(git diff --name-only --diff-filter=U | grep '\.go$')   # 应无输出
go build ./...
git add -A && git commit
```

`vendor/upstream/*` 不必手动管：`.github/workflows/upstream-archive.yml` 每天跑一次；
要立刻补齐就 `make upstream-archive`（只往前，不跟上游的 force-push）。

## 2. 构建

```bash
make preview        # 内部依次：power-meter-build → balance-board → build → ./magpie web
```

分段做：

| 命令 | 产物 |
|---|---|
| `make power-meter-build` | `third_party/power-meter/dist/server.js`（tsc；首次会 `npm ci` 装依赖） |
| `make balance-board` | 把 `dist/` + `public/` 整棵装进 `~/.config/magpie/powermeter/`（sidecar 的落点） |
| `make build` | `./magpie`（本机二进制） |
| `make app` | 仓库根下的 `magpie plus.app`（未签名、未公证；只用来本地试） |
| `make install-app` | 装到 `/Applications/magpie plus.app`，并把仓库里那份删掉——**只留一份** |

`make balance-board` 只覆盖 `dist/` 与 `public/`，**不动**同一目录下的 `.env` 与 `accounts.json`。

## 3. 网页端预览（确认在这一步）

```bash
make preview
```

它开两个端口，都是预览自己的：

- 页面 `127.0.0.1:3436`（`PREVIEW_ADDR` 可改），打印一行
  `magpie web on http://127.0.0.1:3436/?k=…`；
- 网关 `127.0.0.1:3437`（`PREVIEW_GATEWAY`，由 `MAGPIE_ADDR` 传进去）。

**必须点带 `?k=` 的完整链接**，否则会被要求重新登录。页面左下角应显示
`网关 127.0.0.1:3437`——那是这次构建自己的网关。若左下角是 `3425`、日志写
`the gateway on http://127.0.0.1:3425 is served by another magpie`，
说明预览用的是官版 `magpie.app` 的网关，这一轮验不到新构建的网关代码。

为什么分成两个端口：本机 `/Applications` 里的官版 magpie 通常占着 3425，
agent 的请求也都指向它；`MAGPIE_ADDR=3437` 让新构建另起一个网关，
既不动官版、不抢 agent 流量，页面又确实跑在新代码上。

预览要看的东西：

1. 左侧导航「观测」组的 **余额看板** 能开，卡片和到期时间线有数据；
2. 页面右上「余额看板」开关打开后，sidecar 起来（`/api/powermeter/summary` 有响应）；
3. Routing 页里 `expiry` 这种按批次到期排的路由，行上有 `expires`；
4. 这次更新/新功能直接相关的那个页面（例如上游新功能、设置项）。

**两个 magpie 同时开是正常的**：配置目录故意共用（账号、密钥、用量历史只登录一次），
代价是网关只有一个、设置后保存的赢、两边都开余额页会各拉一个 sidecar（平台请求翻倍）。
细节见 [FORK.md §2.2](../FORK.md)。

关掉预览：Ctrl-C。

## 4. 确认之后：构建桌面 App

```bash
make install-app          # 装到 /Applications，并把仓库里的副本删掉
open "/Applications/magpie plus.app"
```

- App 名 / bundle id 是 `magpie plus` / `com.a1ether.magpie-plus`，与官版 `magpie.app` 可共存；
- 包内可执行文件仍叫 `magpie`（`magpie://` 链接、终端里的 `magpie` 都靠它）;
- 未签名未公证，被 Gatekeeper 拦就右键 → 打开；
- 能验托盘（菜单栏里应有「余额看板」一项），这是网页端验不到的部分。

重新构建前不必先关掉旧 App，但要先退出正在跑的 `magpie plus`，否则拷贝会失败（文件在使用中）。

## 5. 新功能开发流程

和更新同样的顺序，只是第 1 步换成写代码：

```bash
git switch -c feature/<名字>
# 改代码：magpie 侧改 internal/…；power-meter 侧见下面的规矩
make preview                       # 网页端看效果
# 确认无误、测试通过
git commit && git push -u origin feature/<名字>   # 之后合回 main
make install-app                   # 要装成桌面 App 再出
```

**改 power-meter 的代码**：首选在 `~/DevSpace/power-meter` 仓库里改、提交、推送，
再回到本仓库 `make update-power-meter` 拉进来。直接改 `third_party/power-meter/` 也能跑，
但要在下次 `pull` 前用
`git subtree push --prefix third_party/power-meter power-meter main`
送回上游仓库，否则两边会分叉出冲突。

**测试**（改动大时按这个顺序，机器上同一时间只跑一套）：

```bash
go vet ./...
go test -timeout 45m ./...          # 默认 10m 会在 internal/gateway 超时
make test-ui                        # internal/gui/tests：Playwright 的 Chromium 与 WebKit
```

**GUI 测试按改动范围跑，不要每次都跑整套**。整套 943 个文件、并发 2 要跑约
**2 小时**，而一次二开通常只碰一个插件页。只跑碰得到的文件：

```bash
NODE_PATH=/tmp/pwrun/node_modules node --test \
  internal/gui/tests/balance-board.test.cjs internal/gui/tests/i18n-keys.test.cjs
```

什么时候非跑整套不可：改了 `app.js`、`app.css`、核心 i18n 词表、`index.html`
的页面骨架，或者**加了一个新的 API 调用**——那时别的页面的红只有整套看得见
（LESSONS.md 里 10-15、10-16 都有这样的例子）。

**本机已知红**（2026-11-12 在合并前的 `f8c969d85` 与合并后的 `326eed4e8` 上各跑一遍
`./internal/gateway/... ./internal/gui/...`，逐条复现，与二开无关）：

| 测试 | 原因 |
|---|---|
| `TestDockReopenKeepsTheWindowsSpace`、`TestCoveredWindowStaysUp` | AppKit 真窗口最小化，非交互会话里等不到 |
| `TestProxyCheckSaysAProxyPassedBy` | 系统代理开着（`scutil --proxy` 读到 Clash 的 7890），测试假定直连 |
| `TestServeWSLListensBesideLoopback` | 本机 `::1` 有应答 |
| `MarshalRaw` 两个测试、`FuzzMarshalRaw`、`TestCodexFittedImagesPastTheBudget` | 本机 Go 1.27.4 的 `encoding/json` 与 CI 的 1.26.x 不同 |

**整套一起跑才红、单独跑全绿**的一批（2026-11-12 记录，机器负载高时更明显）：
`TestForeignSealedItemsAfterAColdSwitch`（6 个子用例）、`TestAffinityKeepsAnHourCachePastFiveMinutes`、
`TestChatGPTConversationStaysPastFiveMinutes`、`TestClaudeConversationKeepsItsAccountsCache`、
`TestDeepSeekConversationStaysPastFiveMinutes`、`TestLaneLimitRoutes`、`TestSessionReadsRoutes`。
它们在合并前、合并后、上游自己的树上都是单独跑全绿，整套里才红——是负载下的时间假设，
不是这次合并带来的。

判断一条红是不是这次改动带来的：在合并前的提交上单独跑同一个测试，比结果，
而不是看它「看着像环境问题」。

**GUI 测试另有 25 个文件本来就是红的**（清单与依据见 [FORK.md §11](../FORK.md)），
另有两件事会让整套看起来比实际更红：

- `mobile-web.test.cjs` 比的是 `BASE_REF`，默认 `origin/main`——本仓库的
  `origin/main` 是合并前的 main，所以它的桌面截图必然全红；
- 并发 4 时会出现只在这一轮红的用例，单跑 2/2 全绿（`gateway-key-models` 的
  chromium en 就是）。判抖动就单跑那个文件、跑两次。


上游的 [代码标准](code-standards.md) 与 [LESSONS.md](../LESSONS.md) 对二开同样适用：
修一个 bug 要覆盖同类的其它位置；红测试当场修、不要「和 main 一样」放过去；
提交体里写清跑了什么、手工破坏验证了什么、没试什么。
