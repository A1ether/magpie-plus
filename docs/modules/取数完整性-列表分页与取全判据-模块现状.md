# 取数完整性规范 —— 列表分页与「取全」判据

> 文档类型：模块现状（跨适配器取数约定）
> 关联模块：平台适配器 / 取数完整性
> 创建时间：2026-10-26
> 最后更新：2026-10-26
> 当前状态：已确认
> 关联改动文件：`src/lib/pagination.ts`、`src/cli/test-pagination.ts`、`src/providers/codearts.ts`、`src/providers/codebuddy.ts`、`src/providers/minimax.ts`

---

## 1. 结论先行

**任何「列表」型上游接口都必须假定它分页，并且必须显式回答「我取全了吗」。**
本项目把这件事收敛到唯一入口 `fetchAllPages()`（`src/lib/pagination.ts`），
手写 `for (page = 1; page <= N; page++)` 的翻页循环视为**缺陷**。

反面教材（已发生的真实事故）：CodeArts 活动逐笔接口不带参数只返回默认页 20 条，
账号有 29 笔「每日签到领积分」时缺 9 笔（9000 积分）。因为卡片上有一条
「账户级桶 − 逐笔合计」的对账差额调节项，缺额被它**静默吸收**，
界面上看起来完全正常——只是钱被算成了一条来路不明的「未明细部分」。
详见 `docs/fixes/CodeArts-活动奖励逐笔分页截断-修复方案.md`。

---

## 2. 为什么这类 bug 特别危险

| 特征 | 说明 |
| --- | --- |
| 不报错 | 接口返回 200、字段齐全、结构正确，解析层完全看不出问题 |
| 不掉字段 | 少的是「第 21 条以后」，类型上无法体现 |
| 有伪装 | 聚合桶对账会把缺口补成一条看起来合理的调节项 |
| 条件触发 | 只在「某天数据超过一页」时出现，日常账号可能永远不触发 |
| 影响下游 | 缺口批次丢了各自真实的 `expireAt`，连带「最快到期」判断失真；日级用量「获取」维度少算 |

结论：**不能靠「看起来对」判断，必须靠显式的不变式。**

## 3. 使用方式

```ts
import { fetchAllPages, incompleteNote } from '../lib/pagination.js';

const result = await fetchAllPages<Item>({
  pageSize: 100,
  maxPages: 10,                        // 防御上游忽略分页参数
  keyOf: (item) => item.id,            // 跨页去重 + 「零新增」判据
  label: '某平台 明细',                 // 仅用于错误信息
  fetchPage: async (page) => {
    const body = await call(page);
    return { items: parse(body), total: readTotal(body) };  // total 拿不到给 null
  },
});

if (!result.complete) {
  // 二选一（必须选一个）：
  //   ① 退回聚合 / 本地采样口径，并说明原因
  //   ② 在 note 里明写未取全：incompleteNote(result)
}
```

### 3.1 取全判据（`complete` 何时为 true）

| 场景 | 判据 | 结果 |
| --- | --- | --- |
| 有 `total`，已取条数 ≥ total | 达到 total | `complete = true` |
| 有 `total`，短页但条数 < total | 上游按 status 过滤了部分记录 | `complete = false`（**不伪装成取全**） |
| 无 `total`，短页 | 后面不会再有数据 | `complete = true` |
| 无 `total`，整页且翻到上限 | 可能还有更多 | `complete = false` |
| 每页零新增 | 分页参数未被识别 | `complete = false`，`stoppedBy='no-progress'` |
| 首页请求失败 | 交给调用方降级 | **抛出**（不伪装成空列表） |
| 次页及以后失败 | 保留已取数据 | `complete = false`，`stoppedBy='error'` |

### 3.2 分页参数名不确定时

先按最可能的命名探测，**必须保留「不带参数」的兜底**：命名猜错时至少拿到默认页，
不会因为「加了参数」把整块数据弄丢。参考实现：
`fetchCampaignBenefitEntries()`（`src/providers/codearts.ts`）——`page/size` →
`pageNum/pageSize` → 无参数，取「枚举最多」的那次。

### 3.3 分页进度不能用「过滤后的条数」判定

解析层常常会丢掉无效条目（已用尽批次、金额 ≤ 0 等）。**翻页进度必须按原始条目数 /
`benefitId` 全集判定**，否则遇到「整页都是已用尽批次」时会误判成「已到末页」，
把后面还有的数据全丢掉。参考：`parseCampaignBenefitEntries()` 保留 `amount ≤ 0` 的条目，
过滤发生在批次构建处。

## 5. 回归护栏

`npm run test:pagination`（`src/cli/test-pagination.ts`）—— 8 条离线断言，不发网络请求、不需要凭证：

| 用例 | 钉住的约束 |
| --- | --- |
| 29 条 / 每页 20 | 正常取全，`pages=2` |
| `maxPages=1` 截断 | **少一条就 `complete=false`**（本次事故的回归护栏） |
| 每页同一批 | 不死循环，`no-progress`，且第 2 页即停 |
| 无 `total` + 短页 | 判取全 |
| 短页但 `total` 更大 | 判未取全（防「被过滤」伪装） |
| 首页失败 | 抛出，不伪装空列表 |
| 次页失败 | 保留已取数据 + `complete=false` |
| 无 `keyOf` | 空页即停，不死循环 |

改动 `src/lib/pagination.ts` 或任一调用方后，跑一次即可确认没有回退。

## 6. 检查清单（新增/修改适配器时逐条核对）

- [ ] 该接口返回的是不是「列表」？是 → 必须走 `fetchAllPages()`。
- [ ] 响应里有没有 `total` / `count` 类字段？有 → 读它，别只靠短页判据。
- [ ] 分页参数名是从抓包确认的，还是猜的？猜的 → 保留「无参数」兜底。
- [ ] 翻页进度用的是原始条目数，还是过滤后的条数？（必须前者）
- [ ] `complete === false` 时，是退回了兜底口径，还是在 note 里明写了未取全？（必须选一个）
- [ ] 该维度的 `covers` 声明是否依赖 `complete`？（未取全不得声明覆盖）
- [ ] 跑过 `npm run test:pagination` 了吗？
