## 1. 背景与目标

**结论：把「一卡一账号」平台卡片右上角那个又登录又添加的复合按钮，拆成语义明确的两个按钮——「重新登录」（凭证过期时用）与「删除」（删掉这张卡的账号）；合并型卡片（A1etherOpenAi）保持原样。**

### 1.1 要解决的问题

现在卡片右上角只有一个按钮，文案随平台能力在两种之间切换（`public/app.js:1478`）：

```js
const toggleLabel = loginMeta ? '＋ 登录 / 添加账号' : '＋ 添加账号';
```

它同时承担三件事，而三件事在真实使用里的频率完全不同：

| 语义 | 实际频率 | 现在怎么做到 |
| --- | --- | --- |
| 凭证过期 → 重新登录 | 高（CodeArts / Qoder 登录态会失效） | 点按钮展开面板 → 再点面板里的登录方法按钮 |
| 删除这个账号 | 低，但破坏性 | 展开面板 → 滚到「本平台已配置的账号」→ 找到自己那行 → 点「删除」 |
| 给同平台再加一个账号 | 极低 | 展开面板 → 登录 / 手工表单 |

高频动作藏在两次点击后面，破坏性动作（删除）反而要在一长串账号里辨认，且「＋ 添加账号」这个主色按钮在一张已经有账号的卡片上语义是错的——用户想做的通常不是「再加一个」。

### 1.2 目标

1. 单账号卡片右上角固定两个按钮：**「重新登录」**（次要样式）+ **「删除」**（危险样式）。
2. 「重新登录」= 展开卡片内登录面板（登录方法按钮组 + 二维码 / 链接 + 状态），并保留「手工填写凭证（兜底）」折叠区。
   注意面板里的手工表单走的是 `/api/accounts/add`（**新增账号**语义，粘贴已配置过的凭证会判重报错）；
   刷新本卡凭证只能走登录——同一平台账号重复登录只更新令牌（§2.5）。README 与凭证配置指南都按这个口径写清了。
3. 「删除」= 直接删除**这张卡片代表的那个账号**，沿用现有的二次确认、`.env` 清理与 `.run/` 备份。
4. 合并型卡片（`groupAccounts`，当前只有 A1etherOpenAi）**不变**：右上角仍是「＋ 添加账号」，删除仍挂在每条账号行上（`public/app.js:833`）。

### 1.3 Non-Goals（明确不做）

- 不改任何后端接口：`/api/accounts/remove`（`src/server.ts:421-443`）与 `/api/login/start`（`src/server.ts:534-572`）已能满足两个按钮。
- 不改适配器契约：不新增 `ProviderAdapter` 字段，能力仍由既有的 `manageAccounts` / `login` / `loginMethods` 声明驱动（`src/providers/index.ts:110-176`）。
- 不在卡片上提供「重命名账号」「停用账号」——两者都没有后端接口。
- 不动顶栏「平台与账号」弹窗：它仍是「给一个还没有账号的平台首次添加」的唯一入口，也是同平台加第二个账号的入口。
- 不新增浮动 toast 组件（见 §7.2）。

## 2. 现状调研

### 2.1 卡片右上角按钮的唯一来源

按钮写在卡片模板里，默认 `hidden`，由 `renderManage` 按能力决定是否显示：

- `public/index.html:185-191`：`.card__balance` 里一个 `.manage__toggle`，初始文案「＋ 添加账号」。
- `public/app.js:695-697`：`buildCard` 克隆 `#manage-template` 后调用 `renderManage(manageRoot, cardTarget(provider), { toggle: node.querySelector('.manage__toggle') })`。
- `public/app.js:1327`：`toggle.hidden = !provider.manageAccounts` —— 不可管理的平台（MiniMax / custom）整张卡没有这个按钮。
- `public/app.js:1479-1514`：`collapse()` / `expand()` 只改 `toggle.textContent` 与 `aria-expanded`，点击即切换 `state.manageOpen`（键为 `cardKeyOf(provider)`）。
- `public/styles.css:1101-1105`：`.manage__toggle { margin-left: auto; align-self: center; }` 把它推到额度行右侧。

### 2.2 展开后的面板内容（本次不动）

`#manage-template`（`public/index.html:247-300`）里三块：

| 区块 | 渲染逻辑 | 说明 |
| --- | --- | --- |
| `.login` | `renderLogin()`，`public/app.js:1052-1237` | 按 `/api/providers` 的 `loginMethods` 渲染 N 个方法按钮；`loginBox.hidden = !loginMeta`（`public/app.js:1356`） |
| `.manage__manual` | `public/app.js:1357-1365` | 有登录能力时 summary 改成「手工填写凭证（兜底）」 |
| `.manage__hidden` | `renderConfiguredAccounts()`，`public/app.js:1613-1646` | 列出本平台全部已配置账号（含停用 / 缺凭证），每行一个「删除」 |

登录会话进行中时，`public/app.js:1476` 会强制把管理区保持展开（二维码住在里面）。

### 2.3 删除链路已经可复用

```
buildRemoveButton(provider, entry, target)   public/app.js:862-870
  └─ removeAccount(provider, entry, target)  public/app.js:957-982
       ├─ window.confirm(平台名 + 账号名 + 「会清掉 .env 里不再被引用的变量，改动前备份到 .run/」)
       ├─ POST /api/accounts/remove { provider, accountId: entry.id }
       └─ target.refresh()  → 卡片是 load(true)，弹窗是重拉总览
```

关键点：**`entry.id` 就是 `accounts.json` 的 `displayName`**（`src/types.ts:141-145`），后端按它唯一定位（`src/account-store.ts:1010-1027`）。而单账号卡片的 `provider.accountId` 同样是 `displayName`（`src/service.ts:309`、`src/providers/base.ts:464`），所以卡片级删除只要构造 `{ id: provider.accountId, label: provider.displayName }` 传进 `removeAccount` 即可，无需新接口。

### 2.4 合并卡片的身份下移（决定分流条件）

`src/aggregate.ts:98-120`：`finalizeCard` 把 `accountId` 置空，身份下移到 `entries[].id`。因此：

- **卡片级没有单一账号身份** → 卡片级「删除」无从下手，只能保持条目行删除；
- 判定条件用快照的 `provider.groupAccounts === true`（`src/types.ts:166-171`），并以 `entries.length > 0` 兜底。

A1etherOpenAi 同时是唯一「合并 + 无登录能力」的平台（`src/providers/a1etheropenai.ts:75-79`，未声明 `login`），与用户确认的取舍一致：右上角保留「＋ 添加账号」。

### 2.5 重新登录为什么不需要后端改动

`landLoginAccount` 按 `options.loginAccountId`（平台账号身份）去重：**同一平台账号重新登录只刷新令牌、保持原 `displayName`；换一个账号登录才新建条目**（`src/account-store.ts:790-796`、`823`、`855`、`910-941`）。这正是「凭证过期 → 重新登录」想要的语义，卡片不会变成两张。

## 3. 方案设计

### 3.1 整体思路

**按钮的可见性与语义在 `buildCard` 一次算清，展开/收起与状态文案仍由 `renderManage` 统一维护**——不新增第二套状态机，避免与登录轮询的强制展开逻辑打架。

`buildCard` 只负责把三个按钮节点作为 `options.cardActions` 交给 `renderManage`，分流在那里一次算清（与展开态、登录会话状态同源，避免两处判断）：

```
grouped = provider.groupAccounts === true || (provider.entries ?? []).length > 0
if (!provider.manageAccounts)        → hideCardActions()：容器 + 三个按钮全 hidden
else if (grouped)                    → 只显示「＋ 添加账号」（现状不变，remove 隐藏）
else if (loginMeta)                  → 「重新登录」+「删除」
else                                 → 「＋ 登录 / 添加账号」或「＋ 添加账号」+「删除」（防御分支）
if (!meta)                           → hideCardActions()：能力清单没拉到，连删除也不给
```

`hideCardActions()` 连 `.card__actions` 容器一起隐藏：容器带 `margin-left:auto`，留着会在额度行右侧占一个 flex gap（`.card__actions[hidden] { display: none }` 已补，见 §8.2）。

### 3.2 数据流

```
点「重新登录」
  → state.manageOpen.add(cardKey)         （复用现有展开态，跨重建保留）
  → renderManage 展开 .manage：.login 方法按钮组 + .manage__manual 折叠兜底
  → 用户点某个登录方法 → POST /api/login/start { provider }（不变）
  → 轮询 /api/login/poll → 终态 ready → landLoginAccount 按 loginAccountId 更新原条目
  → load(true) 重取 → 卡片刷新（displayName 不变，卡片还是那一张）

点「删除」
  → removeCardAccount(provider, target, paintRemove)
      ├─ state.deleting.add(cardKey) → 按钮变「删除中…」+ disabled
      ├─ 本平台有活跃登录会话 → 先 POST /api/login/cancel 并清 state.login
      │   （否则会话终态落库时找不到原条目，会把刚删的账号又新建回来）
      └─ removeAccount(..., onSettled = flashNotice)
           → window.confirm（平台名 + 账号名 + 「会清 .env / 备份 .run/」）
           → POST /api/accounts/remove { provider, accountId: provider.accountId }
           → removeManagedAccount 移除条目 + 清理不再被引用的 .env 变量 + 备份 .run/
           → load(true) 重取 → 卡片消失（该平台还有别的账号时只剩别的卡）
           → 结果提示在 refresh **之后**写入「诊断」区（见 3.4）
      → finally：state.deleting.delete + renderGrid（清掉「删除中…」残留）
```

### 3.3 职责划分

| 层 | 改动 | 说明 |
| --- | --- | --- |
| `public/index.html` | `.card__balance` 内改为 `.card__actions` 容器，放三个按钮（均默认 `hidden`） | 骨架改动，需强刷 |
| `public/app.js` | `buildCard` 传 `cardActions`；`renderManage` 统一维护可见性/文案/禁用态；新增 `removeCardAccount()`、`flashNotice()`、`hideCardActions()`；`removeAccount()` 增 `onSettled` 参数并改为返回 `'cancelled' \| 'removed' \| 'failed'` | 逻辑集中在 `renderManage` 的「卡片右上角按钮组」一节 |
| `public/styles.css` | 新增 `.card__actions` 与 `.card__actions[hidden]`；`.manage__toggle` 的 `margin-left:auto` 上移到容器 | 纯布局 |
| 后端 | **无改动** | 见 §2.3、§2.5 |
| 适配器 | **无改动** | 能力仍由 `manageAccounts` / `loginMethods` 声明驱动 |

### 3.4 「删除」结果提示落在哪

卡片级删除成功后这张卡就没了，`state.manageMessages`（按卡片键存）随之失去宿主，提示会静默丢失。取舍：

- 删除**失败**必须让人看见（后端可能返回 404「找不到账号」/ 409「displayName 重复无法定位」，`src/account-store.ts:1015-1027`）；
- 复用现有「诊断」区（`public/index.html:130-136`，副标题就是「凭证与配置问题会在这里提示」），与剪贴板失败等提示同一套 `diag` / `diag--warn` 样式（`public/styles.css:1708-1723`），不引入新的浮层组件。

**写入时机是关键**：`renderDiagnostics` 每次都 `replaceChildren()` 整个诊断区（`public/app.js:2132-2133`），而删除的 `refresh()` 会走 `load(true)` → `render()` → `renderDiagnostics`。所以两种落点的时机相反，由 `removeAccount` 内部的 `settle()` 统一分流：

| 落点 | 时机 | 原因 |
| --- | --- | --- |
| 管理区结果行（条目行删除 / 弹窗删除） | refresh **之前** `setManageMessage` | 重绘时 `renderManage` 才从 state 里把它画出来 |
| 诊断区（卡片级删除） | refresh **之后** `flashNotice` | 先写会被 `renderDiagnostics` 抹掉 |

条目行删除与弹窗内删除的提示路径保持不变（它们的宿主卡片/弹窗还在）。

### 3.5 按钮状态与文案

| 状态 | 「重新登录」/「＋ 添加账号」 | 「删除」 |
| --- | --- | --- |
| 面板收起 | `重新登录` | `删除` |
| 面板展开 | `收起`（沿用现有约定，`aria-expanded=true`） | `删除` |
| 登录会话进行中（`state.login.providerId` 命中本卡、会话未到终态） | `登录中…`，`disabled`，面板被强制展开 | `删除`（可用；点击会先取消会话再删，见 §3.2） |
| 请求中 | 不变 | `删除中…`，`disabled` |
| 用户在确认框点「取消」 | 不变（不重绘，手工表单已输入的内容不被清掉） | 恢复 `删除` |
| 平台无 `loginMethods`（当前不存在这种单账号平台，防御分支） | `＋ 添加账号`（保住进入表单的入口） | `删除` |
| 合并卡片（A1etherOpenAi） | `＋ 登录 / 添加账号` 或 `＋ 添加账号` | 隐藏（删除在每条账号行上） |
| 不可管理 / 能力清单没拉到 | 容器整体隐藏 | 同左 |

「重新登录」与「＋ 添加账号」共用同一个 `onToggle` 开关（同时只有一个可见），展开态仍是 `state.manageOpen`。

## 4. 接口设计

**结论：无新增、无变更接口。** 两个按钮复用既有端点：

| 按钮 | 方法 | 路径 | 入参 | 出参 | 错误码 |
| --- | --- | --- | --- | --- | --- |
| 重新登录 | POST | `/api/login/start` | `{ provider, method? }` | `{ ok, session }` | 404 未知平台 / 403 未开放登录（`src/server.ts:546-557`） |
| 重新登录（轮询/取消） | GET / POST | `/api/login/poll` `/api/login/cancel` | `?id=` / `{ id }` | `{ ok, session }` | 404 会话已清理 |
| 删除 | POST | `/api/accounts/remove` | `{ provider, accountId }` | `{ ok, name, removedEnvLines, backupDir }` | 403 未开放增删 / 404 找不到账号 / 409 displayName 重复 / 500 写入失败 |

三者都过 `privilegedGuard`（只允许本机 + 自定义头 `X-Power-Meter-Intent`），前端调用方式不变（`loginRequest` / `manageRequest`）。

`ProviderAdapter` 契约**不扩展**：卡片形态判定用快照里已有的 `groupAccounts`，能力判定用已有的 `manageAccounts` / `loginMethods`。

## 5. 数据模型

**结论：`types.ts` 契约、`accounts.json`、`.env` 均无变更，不涉及配置迁移。**

用到的既有字段（只读）：

| 字段 | 来源 | 用途 |
| --- | --- | --- |
| `ProviderSnapshot.groupAccounts` | `src/types.ts:167` | 卡片形态分流 |
| `ProviderSnapshot.accountId` | `src/types.ts:159-166` | 卡片级删除的定位键（= `displayName`） |
| `ProviderSnapshot.manageAccounts` | `src/types.ts:172` | 按钮是否出现 |
| `ProviderSnapshot.entries[]` | `src/types.ts:140-157` | 合并卡片兜底判定 |
| `/api/providers` 的 `loginMethods` | `src/providers/index.ts:131-134` | 「重新登录」是否可用、面板内方法按钮组 |

前端新增的状态只有 UI 层面的两处，均不进任何持久化结构：

- `state.deleting`（`Set<string>`，键同 `cardKeyOf`）：防止「删除」连点导致两次 `POST /api/accounts/remove`；
- 无新增 `state` 字段用于展开态——继续用 `state.manageOpen`。

## 6. 影响面评估

| 影响面 | 结论 |
| --- | --- |
| 适配器 | 零改动；不共用 `lib/` 与 `base.ts`，无回归风险 |
| 聚合逻辑 | 零改动；`groupAccounts` 只被读取 |
| 卡片渲染 | 单账号卡片右上角从 1 个主色按钮变成 2 个按钮（次要 + 危险），额度行右侧视觉重量下降；合并卡片完全不变 |
| 「平台与账号」弹窗 | 不变（`dialogTarget` 不传 `cardActions`，`renderManage` 走原分支） |
| 缓存策略 | 不变（删除后 `load(true)` 与现状一致，后端缓存键按 `provider#displayName`，条目消失即不再取数） |
| 到期时间线 | 不变（删除账号后时间线随下一次聚合自然少一条） |
| 既有 API 消费方 | CLI（`npm run account`）与 `/api/a1etheropenai/accounts*` 不受影响 |
| 用户习惯 | **单账号卡片上不再有「给同平台加第二个账号」的快捷入口**，改走顶栏「平台与账号」；此外登录一个新账号本身也会新建卡片（`landLoginAccount` 的 `updated=false` 分支） |
| 破坏性操作可达性 | 「删除」从「展开面板 → 找账号行」变成一键可达，因此二次确认必须保留且文案要点明会清 `.env`（沿用 `removeAccount` 现有 confirm） |
| `removeAccount` 的三个调用方 | 签名向后兼容：第 4 个参数 `onSettled` 默认 `null`（走管理区结果行，行为不变）；返回值从 `undefined` 变成 `'cancelled' \| 'removed' \| 'failed'`，条目行（`buildRemoveButton`）与弹窗账号列表（`renderConfiguredAccounts` / `buildPlatformRow`）都忽略返回值，不受影响 |
| 删除确认框的平台名 | 由 `target.provider.displayName` 改为**优先取 `/api/providers` 的适配器名**：单账号卡片的 `displayName` 是「CodeBuddy · 账号 1」，原写法会拼出「删除 CodeBuddy · 账号 1 账号「CodeBuddy · 账号 1」？」这种重复；合并卡片与弹窗路径的文案不变（那里本来就是平台名） |
| 仓库文档 | 三处描述旧按钮文案的活文档已同步：`README.md`（接入账号、多账号、看板添加三节）、`docs/凭证配置指南.md`（开头速查、手工表单口径）、`docs/modules/项目整体-代码Wiki.md`（§10.2 上手步骤、§11 前端函数表、变更记录 +1）。历史 `docs/plans/`、`docs/fixes/` 里的旧文案是当时的记录，不回溯修改 |

## 7. 风险与备选方案

### 7.1 主要风险与处置

| 风险 | 处置 |
| --- | --- |
| 误删：破坏性按钮上移到一眼可见处 | 保留 `window.confirm`，文案含平台名 + 账号名 + 「清掉不再被引用的 .env 变量」+「改动前自动备份到 `.run/`」；按钮用危险样式（`secret__btn--danger`）与「重新登录」明确区分 |
| `provider.accountId` 为空串（`accounts.json` 没写 `displayName`，`src/config.ts:259-278` 只会告警不阻断） | 按钮仍可用：后端按 `displayName === ''` 匹配，唯一则删成功、重复则返回 409，两条路径都有明确提示；确认框显示「(未命名)」 |
| 登录会话进行中点「删除」 | 删除后 `load(true)` 重绘；`state.login` 仍指向已删账号的会话，终态时 `landLoginAccount` 会因找不到原条目而**新建**一条——因此删除时若本平台有活跃登录会话，前端先 `POST /api/login/cancel` 再删 |
| 登录轮询每 1.5s 重建卡片，按钮状态被覆盖 | 按钮文案/禁用态一律在 `renderManage` 内按 `state.login` 计算（与现有 toggle 同一处），重建即重算，天然一致 |
| **实施中发现**：`removeAccount` 内部的 `refresh()` 会重建卡片，而那时 `state.deleting` 还没清 → 重建出的「删除」按钮永久停在「删除中…」+ `disabled` | `removeCardAccount` 的 `finally` 里在清掉 `state.deleting` **之后**再 `renderGrid(state.data)` 补一次重绘；用户在确认框点「取消」时不补（重建会清掉手工表单里已输入的内容），因此 `removeAccount` 改为返回 `'cancelled'` 以便区分 |
| **实施中发现**：`.card__actions` 容器带 `margin-left:auto`，三个按钮全隐藏时容器仍占一个 flex gap，额度行右侧留空位 | 容器一并 `hidden`，并补 `.card__actions[hidden] { display: none }`（类选择器的 `display:flex` 会盖掉 UA 的 `[hidden]` 规则，与仓库既有的 `.usage[hidden]` 同类问题） |
| `index.html` 骨架改动被浏览器缓存 | 生效前提里写明需强刷（⌘⇧R） |

### 7.2 被否决的备选方案

| 方案 | 否决原因 |
| --- | --- |
| 保留复合按钮，只在展开的面板顶部加「删除本账号」 | 没解决「高频的重新登录藏在两次点击后」，破坏性动作仍在账号列表里找 |
| 「删除」用行内二次确认（按钮变「确认删除？」）替代 `window.confirm` | 与仓库现有的删除交互（条目行、弹窗、A1etherOpenAi 专用路径）不一致，会出现两套确认范式 |
| 新增浮动 toast 组件承载删除结果 | 需要新 CSS/层级管理，而「诊断」区已经是既有的提示落点且语义吻合（见 §3.4） |
| 后端新增 `/api/accounts/relogin`，把「重新登录」做成一步到位 | `/api/login/start` 已经就是这个语义；新增接口只会多一层转发，且登录必须是异步会话（二维码/网页抓取），无法一步返回 |
| 合并卡片右上角也放「删除」 | 卡片级 `accountId` 为空（`src/aggregate.ts:102`），无法定位到唯一账号；用户已确认保留「＋ 添加账号」 |
