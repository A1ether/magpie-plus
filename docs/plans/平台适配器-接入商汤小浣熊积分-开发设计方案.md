## 1. 背景与目标

**结论：把商汤小浣熊网页端（`https://xiaohuanxiong.com/work/home`）的积分余额、积分构成与到期时间接进看板，让「每日赠送 / 每月赠送 / 加油包 / 奖励积分」参与「最快到期」排序。**

### 1.1 要解决的问题

小浣熊的积分不是一笔糊涂账，而是四类各自独立的桶（官方《积分规则说明》与定价页均写明）：

| 积分类型 | 额度 | 有效期规则 |
| --- | --- | --- |
| 每日赠送积分 | 免费版 300/日；个人升级版 500/日；企业版 1000/日/人 | 默认发放当日 24:00 失效；**当天登录后延长至 7 个自然日**，多笔分别计算 |
| 每月赠送积分 | 个人升级版 10,000/月；企业版 30,000/月/人 | 仅限当前订阅周期，进入下一周期清零重发 |
| 加油包积分 | 小包 ¥9.9 / 500、大包 ¥19.9 / 1,200（升级版专享） | **永久有效**，可跨月；升级版到期或降级后冻结，重新升级可恢复 |
| 奖励积分 | 上线礼包、兑换码、官方活动 | 到账后 1 年内有效 |

看板的价值就在「哪个桶先过期、还剩多少」，因此必须把这四类分开成 `CreditLot`，而不是只显示一个总额。

### 1.2 达成效果

- 卡片：余额 = 账户级可用积分；批次列表逐桶展示（每日 / 每月 / 加油包 / 奖励），带各自到期时间；「加油包冻结」时如实标注。
- 到期时间线：每日 / 每月 / 奖励三类按各自 `expiresAt` 参与「最快到期」排序；加油包永久有效，不生成到期事件。
- 每日用量 / 增量：直接用平台「积分明细」逐笔记录（`/api/web/points/v2/bills`），覆盖 `use` 与 `grant` 两个维度，不再依赖本地采样。
- 人民币估值：按加油包官方单价折算（见 §6）。
- 账号入口：看板「网页端登录」自动打开调试 Chrome 抓取登录态；也支持 `npm run capture -- xiaohuanxiong` 与手工粘贴。

### 1.3 Non-Goals（明确不做）

1. **不实现「扫码登录」**：小浣熊的二维码登录走 `https://xiaohuanxiong.com/login/mp?code=...` + 服务端轮询换取令牌，属于另一套私有协议；本轮先用「网页端登录（CDP 旁听真实请求）」与手工凭证，稳定后再评估。
2. **不实现签到 / 领取加油包 / 购买**：只读，绝不调用任何写接口（与 MiniMax 签到状态同一原则）。
3. **不做积分「逐批次剩余」的账本重放**：`bills` 是流水（发放 / 消耗 / 过期 / 退款），不是批次剩余；按流水重放推断每笔剩余既不可靠也会与账户级余额打架。改为「余额给数量、明细给到期时间」的组合口径（见 §5.4）。
4. **不接入企业控制台（`office-console.xiaohuanxiong.com`）**：企业版的「用量看板」是另一套域名与鉴权，本轮只覆盖个人版 / 个人升级版网页端。企业版账号若登录网页端，仍能读到 `available_points` 与 `enterprise_topup_points`，但企业成员维度不展开。

### 2.2 平台接口取证

官方文档（`doc.xiaohuanxiong.com` 积分规则页）**没有公开任何查询接口**，只说明「账户区域 / 设置 → 资源用量」可查看余额、构成与明细。接口来自两处交叉取证：

1. **桌面客户端静态取证**：`/Applications/商汤小浣熊.app/Contents/Resources/app.asar` 的 webpack 产物里含完整请求封装（`class ... { static get baseUrl(){ return `${origin}/api/web/points` } ... }`、`getBalance()`、`getBills()`、`createHeaders()`、`refreshTokenRequest()`）。
2. **线上端点实测**（未登录请求，只验证路由存在与错误形态）：
   - `GET /api/web/points/v1/balance` → `401 {"code":200001,"message":"authorization_empty_error"}`
   - `GET /api/web/points/v2/bills?paging.limit=1&type=all` → `401` 同上
   - `POST /api/web/auth/v1/refresh`（空 body）→ `400 {"code":100002,"message":"params_invalid_error"}`（路由存在）
   - `GET /api/web/auth/v1/user_info` → `401`
   - `GET /api/web/office/v3/entitlement_info` → `404`（说明 `entitlement_info` 挂在 `auth` 前缀下）
   - **Cookie 单独不鉴权**：`Cookie: raccoon_token=…` → `200001 authorization_empty_error`；`Authorization: Bearer …` → `200003 authorization_verify_error`。即**鉴权只看 `Authorization: Bearer`**。

## 3. 方案设计

**结论：新增 `xiaohuanxiong` 适配器，凭证为「访问令牌（必填，可由 Cookie 推导）+ 会话 Cookie（可选）+ 刷新令牌（可选）」；余额取账户级接口，到期时间取积分明细 + 订阅信息，用量/增量取明细流水。**

### 3.1 整体思路

```
xiaohuanxiong.com 网页端
   ├── GET /api/web/points/v1/balance          → 四类积分的「当前剩余」（数量权威）
   ├── GET /api/web/points/v2/bills?type=income→ 发放记录的 expire_at（到期时间权威）
   ├── GET /api/web/auth/v1/entitlement_info   → 订阅到期（每月积分兜底到期时间）
   └── GET /api/web/points/v2/bills?type=all   → 逐笔流水（用量 / 增量）
                     │
                     ▼
   src/providers/xiaohuanxiong.ts  probe() → ProviderSnapshot（credits[] / balance / note）
                                   fetchUsageLedger() → UsageLedger{covers:{use:true,grant:true}}
                     ▼
   service.ts（缓存 + 日级装配） → aggregate.ts（排序 + 到期时间线 + 折人民币） → public/app.js
```

### 3.2 职责划分

| 层 | 职责 |
| --- | --- |
| 适配器 | 取数、信封校验、令牌续期、把四类积分拆成 `CreditLot`、把流水归一成 `UsageRecord` |
| 编排层 | 并发、TTL 缓存、失败降级（沿用现状，无改动） |
| 聚合层 | 按 `credits[].expiresAt` 排「最快到期」（沿用现状，无改动） |
| 前端 | 按 `/api/providers` 的声明渲染登录 / 表单（沿用现状，无改动） |

### 3.3 鉴权与令牌续期

- `resolveToken(account)`：`credentials.token`（兼容 `Bearer ` 前缀）优先；为空时从 `credentials.cookie` 里按 §2.3 的顺序推导。
- 请求头固定带 `Authorization: Bearer <token>`；`cookie` 存在时一并发送（当前不是必需，但保留以应对上游把会话 Cookie 纳入校验的改版）。
- 401 / 业务码 `200001|200003|200009` 且存在 `refreshToken` → `POST /api/web/auth/v1/refresh {refresh_token}`，拿 `data.access_token` / `data.refresh_token`，通过 `ctx.persistCredentials` 写回 `.env` 后重试一次（与 `codebuddy.ts:471-503` 同一范式）。
- **鉴权判断放在解信封之后**：上游可能用「HTTP 200 + 业务码」表达令牌失效，只在 `fetchJson` 层判 401 会漏掉这种情形。因此 `xhxRequest()` 自己解信封、自己判鉴权码，失败时统一抛成 `HttpError(401)` 再进续期分支。
- **本轮令牌缓存**（`WeakMap<AccountConfig, string>`）：一次 `probe()` 会连打余额 / 明细 / 订阅 / 身份四个接口，若各自拿着旧令牌各续期一次，会把刚轮换出的令牌刷废——与 `codebuddy.ts` 的 `cbRefreshCache` 同一动机。
- **抓取时两种存储都要看**：网页端默认 `NEXT_PUBLIC_STORAGE_TYPE=cookie`，但同一套 Cookie 名也可能落在 localStorage（客户端有 `localstorage` 分支）。`capture` 先读 Cookie 头、再读 localStorage，两者都空才判「未登录」；这一步必须排在「跳过判定」之前。

| # | 方法 / 路径 | 用途 | 关键返回字段 |

| ① | `GET /api/web/points/v1/balance` | 账户级余额与四类构成 | `data.available_points`、`daily_points`、`monthly_points`、`reward_points`、`topup_points`、`topup_frozen`、`enterprise_topup_points` |

### 4.2 错误映射

| 上游表现 | 本项目状态 | 处理 |
| --- | --- | --- |
| HTTP 401 + `code=200001/200003/200009` | `unauthorized` | 有 `refreshToken` 则续期一次；仍失败则卡片显示「登录态已失效」 |
| HTTP 403 | `forbidden` | 直接失败 |
| HTTP 429 | `rateLimited` | 直接失败（不重试） |
| `code` 非 0 且非鉴权码 | `error` | 把 `message` / `details` 原样带出 |
| 网络层失败 | `unavailable` / `error` | 沿用 `fetchJson` 的直连兜底 |

无。`ProviderAdapter` 的 `probe` / `fetchUsageLedger` / `login` / `manageFields` 均已存在，本次只是新增一个实现。

## 5. 数据模型

**结论：`Currency` 沿用 `CREDITS`（与 MiniMax / CodeBuddy 的「积分」口径一致，便于统一折人民币）；四类积分各生成一个 `CreditLot`，金额取账户级各桶剩余，到期时间取明细 / 订阅信息。**

### 5.1 `types.ts` 变更

无。用到的既有契约：

| 契约 | 本次用法 |
| --- | --- |
| `ProviderSnapshot.balance` | `{ amount: available_points, currency: 'CREDITS' }` |
| `ProviderSnapshot.credits[]` | 四类积分各一条，`basis: 'remaining'` |
| `ProviderSnapshot.windows[]` | **留空**：平台没有「周期上限」概念，不画假进度条 |
| `ProviderSnapshot.plan` | 订阅标签（`个人升级版 / 企业版 / 免费版`，由 ③ 推导；取不到为 `null`） |
| `DailyUsage` | 由 `fetchUsageLedger` 提供 `use` + `grant` 两维上游值 |

### 5.2 批次（`CreditLot`）口径

| 批次 | `label` | `amount` | `expiresAt` |
| --- | --- | --- | --- |
| 每日赠送 | `每日赠送积分` | `daily_points` | ① 明细里 `daily_grant` 的**最早未过期 `expire_at`**；② 取不到 → 当天 23:59:59（+08:00） |
| 每月赠送 | `每月赠送积分` | `monthly_points` | ① 明细里 `monthly_*` 的 `expire_at`；② 取不到 → ③ 的订阅到期时间 |
| 加油包 | `加油包积分` | `topup_points` | `null`（永久有效）；`topup_frozen` 为真时在 `note` 里写明「已冻结」 |
| 企业加油包 | `企业加油包（共享）` | `enterprise_topup_points` | `null` |
| 奖励 | `奖励积分` | `reward_points` | 明细里 `reward_*` 的最早未过期 `expire_at`；取不到 → `null` + 备注 |

**为什么金额取余额、到期取明细**：`bills` 是流水，单笔发放的 `points` 是「授予量」而非「该笔剩余」；用账户级 `*_points` 做金额、用流水做到期时间，两个来源各取所长，且金额之和与 `available_points` 天然对得上（见 §5.3）。

### 5.3 对账与备注

- 若 `daily + monthly + reward + topup + enterprise_topup` 与 `available_points` 相差 > 0.5，卡片 `note` 追加一句「积分构成合计 X 与可用总额 Y 不一致，余额以可用总额为准」，便于上游改口径时第一时间发现。
- 批次为空的桶不生成 `CreditLot`（避免 0 元批次污染到期时间线）。
- 过期不是「用量」：`biz_type` 含 `expire` 的流水**不计入** `use`，也不计 `grant`（它们既不是花掉的、也不是到账的），在文档与卡片备注里说明。

### 5.4 为什么不做「逐批次剩余」

流水里的 `biz_id` 对普通记录没有稳定的批次标识；桌面端会话记录还带 `desktop-*:turn-*` 形态的前缀（客户端自己按前缀聚合成会话卡片）。按流水重放剩余会引入三类误差：并发写入顺序、退款记录语义、以及「过期记录与发放记录不配对」。因此明确采用 §5.2 的口径，并在文档标注「单笔批次剩余不可得」。

### 5.5 配置项（`accounts.json`）

```jsonc
{
  "provider": "xiaohuanxiong",
  "displayName": "商汤小浣熊",
  "enabled": true,
  "credentials": {
    "token": "${XIAOHUANXIONG_TOKEN}",
    "refreshToken": "${XIAOHUANXIONG_REFRESH_TOKEN}",
    "cookie": "${XIAOHUANXIONG_COOKIE}"
  },
  "options": {}
}
```

| 键 | 必填 | 说明 |
| --- | --- | --- |
| `token` | 与 `cookie` 二选一 | 网页登录态令牌；`capture` / 网页端登录会自动写入 |
| `cookie` | 否 | 完整 Cookie 头；用于推导令牌，并在上游要求会话 Cookie 时一并发送 |
| `refreshToken` | 否 | 令牌续期用；缺失时令牌过期需重新登录 |
| `options.origin` | 否 | 覆盖 origin（自定义代理 / 测试环境用） |
| `options.site` | 否 | 预留：`cn`（默认）。小浣熊目前只有国内站 |

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 上游为内部接口，可能随版本改路径 / 字段 | 卡片报 `notFound` / `error` | 路径与字段集中为常量；解析全部走 `pick` 多候选键；失败时把上游 `message` 原样带出 |
| `biz_type` 枚举未穷举（只实测到 `daily_grant` / `daily_expire`） | 每月 / 奖励批次可能拿不到到期时间 | 关键字匹配 + 订阅信息兜底；取不到就**不编时间**，在 `note` 里写明「到期时间未取到」 |
| 每日积分「当天登录延长至 7 天」 | 用当天 23:59 兜底会低估可用时间 | 优先用明细 `expire_at`（登录后上游会给出延长后的时间）；兜底仅在明细不可用时启用，并标注 |
| 令牌在浏览器里会被轮换（IAM refresh） | 长驻服务拿到旧令牌 → 401 | 实现 refresh + `persistCredentials` 写回；`capture` 可随时重抓 |
| 网页端登录依赖调试 Chrome | 无 Chrome / 端口被占用时不可用 | 与 CodeBuddy 同一套 `ensureDebugChrome`，失败给出可操作提示；保留手工粘贴令牌 |
| 企业版成员维度未覆盖 | 企业账号只看到个人桶 | 明确写进 Non-Goals 与卡片备注 |

**备选方案与否决理由**

| 方案 | 结论 |
| --- | --- |
| 用 `custom` 声明式适配器（`sessionApi`）接入 | 否决：只能做静态 JSON 路径映射，拿不到「四类积分 + 到期时间 + 明细」的组合口径，也无法做令牌续期 |
| 只展示总额（不拆批次） | 否决：与项目核心目标（最快到期）相悖 |
| 用浏览器 CDP 每次刷新都去页面里取数 | 否决：需要常驻浏览器，刷新成本高；仅在「网页端登录」时用 CDP |

## 9. 验证方式

> 按 `AGENTS.md` §6，本轮只做静态检查（`npm run typecheck` + 代码阅读），**不执行** `npm run probe` / `npm run capture` / 启动服务。

### 9.1 静态检查

| 项 | 命令 | 预期 |
| --- | --- | --- |
| 类型检查 | `npm run typecheck` | 无报错 |
| 引用核对 | 只读检索 | 注册表、抓取目标、`.env` 键名、示例配置四处一致 |

### 9.2 人工自测（需用户在本机执行）

| # | 场景 | 命令 / 操作 | 预期 |
| --- | --- | --- | --- |
| 1 | 抓取凭证 | `npm run chrome:debug` → 登录小浣熊 → `npm run capture -- xiaohuanxiong` | `.env` 写入 `XIAOHUANXIONG_COOKIE` / `XIAOHUANXIONG_TOKEN` |
| 2 | 注册账号 | `npm run account -- --provider xiaohuanxiong --env XIAOHUANXIONG_TOKEN` | 先验证再写入，卡片出现 |
| 3 | 取数 | `npm run probe -- xiaohuanxiong` | 余额 = 页面「资源用量」的可用积分；批次与页面构成一致 |
| 4 | 明细 | 看板卡片「每日用量」区 | 今日用量 / 增量与页面「积分明细」当日记录吻合，来源标注 `upstream` |
| 5 | 网页端登录 | 卡片 →「网页端登录」 | 自动打开调试 Chrome，登录后自动落库 |

### 9.3 回归范围

- 既有平台不受影响（未改共享函数）；建议顺带跑一次 `npm run probe`（全平台）确认无回归。
- 若 `.env` 新增变量为空，`loadConfig` 不应报警（仅被引用且展开为空时才进 `missingEnvVars`，示例里默认不引用）。
