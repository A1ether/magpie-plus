## 1. 背景与目标

**结论：把千问办公网页端（`https://qwenwork.cn/app/settings/usage`）的积分余额、三类积分构成与到期规则接进看板，让「每日刷新积分 / 每月订阅积分 / 长期积分」分别成为可排序的 `CreditLot`，并给出每日消耗与获取。**

### 1.1 要解决的问题

千问办公用量页把可用积分拆成三个彼此独立的桶（`public/app.js` 无关联，证据见 §2.2 的前端产物）：

| 积分类型 | 上游字段 | 有效期规则（上游文案原文） |
| --- | --- | --- |
| 每日刷新积分 | `daily_credits.total_balance` | 「个人版每日赠送积分，每天 00:00 刷新」（移动端：`dailyCreditsDesc`） |
| 每月订阅积分 | `monthly_credits.total_balance` | 「订阅套餐内的积分，当月有效」；刷新时间取 `plan.next_refresh_date` |
| 长期积分（其他积分） | `longterm_credits.total_balance` | 「通过充值或活动获取」「包含积分充值包、新用户注册赠送积分，有效期以具体规则为准」 |

页面把三者之和显示为「剩余可用」（`/user/balance` 的 `balance`）。看板要回答的是「哪一桶先作废、还剩多少」，因此必须拆成三条 `CreditLot`，而不是只显示一个总额。

### 1.2 达成效果

- 卡片：余额 = `/user/balance` 的 `balance`；批次列表逐桶展示每日 / 每月 / 长期，带各自到期时间；三者之和与总额对不上时如实说明（沿用 `xiaohuanxiong.ts` 的对账备注做法）。
- 到期时间线：每日桶按「北京时间当日 24:00」兜底；每月桶按 `plan.next_refresh_date`，取不到（或已是过去）时退回订阅到期 `plan.next_due_date`，两者都没有才按「北京时间本月末 24:00」推算并注明；长期桶只有在积分明细里拿到明确 `expires_at` 时才参与排序，拿不到就**不猜**。
- 每日用量 / 增量：用 `/user/billings` 逐笔流水（`amount > 0` → grant，`amount < 0` → use），覆盖两个维度；未取全则整份退回本地采样。
- 人民币估值：按平台公开的订阅套餐单价折算（见 §6）。
- 账号入口：看板「网页端登录」用 CDP 旁听真实 Cookie；也支持 `npm run capture -- qwenwork` 与手工粘贴 Cookie。

### 1.3 Non-Goals（明确不做）

1. **不实现扫码 / 钉钉 / 阿里云 SSO 登录**：千问办公的登录入口有三条（手机验证码、Google、钉钉/阿里云 SSO），全部走 `https://qwenwork.cn/signin` + 服务端回调，各是一套私有协议；本轮统一用「网页端登录 + Cookie 粘贴」。
2. **不做任何写操作**：不领取每日积分、不充值、不兑换，只读（与 MiniMax / 小浣熊同一原则）。
3. **不覆盖企业版配额**（`/biz/user/v1/settings/enterprise/quota` 与企业组织切换）：企业版按「席位配额 − 已用」展示，口径与个人版的三桶模型不同；本轮只覆盖个人版 / 个人付费版，企业账号登录后仍能读到个人 `balance`，但企业配额不展开。
4. **不解析「积分消耗明细」的分层结构**（`/user/billings/sessions/{id}/turns/{tid}/details`）：逐笔流水已足够支撑日级用量与增量，按模型 / 工具拆分属于另一层展示，不做。

### 2.2 平台接口取证

官方没有任何公开查询 API；证据来自**线上前端产物静态取证**与**未登录端点实测**（只验证路由是否存在、鉴权形态，不带任何真实凭证）：

1. **前端产物**：`https://qwenwork.cn/app/settings/usage` 的 HTML 引用 `/app/assets/index-Dm_Kd17d.js`（3.88 MB，含全部请求封装）与路由分包 `/app/assets/usage-CRM1j6Gf.js` → `/app/assets/usage-B1CFA0X2.js`（用量页组件本体）。
   - `index-Dm_Kd17d.js` 中 `Xe({url:"/user/balance",method:"GET"})`、`/user/wallets`、`/user/info`、`/user/billings`、`/user/plans`、`/user/v2/account-context`、`/user/v2/quota`、`/biz/user/v1/settings/enterprise/quota` 均可读出。
   - **没有 `/user/plan`（单数）端点**：套餐与刷新时间全部来自 `/user/info` 的 `plan` 对象（用量页组件读的就是 `y.data?.plan?.next_refresh_date`，`y = useGetUserInfo()`）。
   - 用量页分包里只有两个新端点：`/user/billings/expirations`（分页取「过期积分」）与 `/user/billings/sessions`（分类明细），以及 `/user/billings/sessions/{id}/turns/{tid}/details`。
   - 用量页组件读取的字段：`balance`、`daily_credits.total_balance`、`monthly_credits.total_balance`、`longterm_credits.total_balance`、`plan.next_refresh_date`、`plan.pid`、`plan.subscription_status`、`plan.next_due_date`、`is_biz`、`nickname`/`username`/`email`/`avatar`。
   - 逐笔流水行字段：`amount`（有符号）、`created_at`、`detail.title`、`source` / `consume_source` / `client_name` / `client_type` / `platform`、`transaction_id`；分页返回 `items[]`、`has_more`、`next_cursor`、`total_pages`。
   - 响应信封：`{ code: "ok", data: … }`，非 `ok` 时 `{ code, msg }`（`Xe()` 封装里 `code==="ok"||"SUCCESS"` 才取 `data`）。
2. **未登录实测**（`curl`，无任何 Cookie / 令牌）：

| 请求 | 结果 | 结论 |
| --- | --- | --- |
| `GET /user/balance` | `401 {"code":"invalid-credential","msg":"Missing or invalid token"}` | 路由存在，需登录态 |
| `GET /user/wallets`、`/user/info`、`/user/billings` | 同上 | 同上 |
| `GET /user/billings/expirations?limit=20` | `404 page not found`（无鉴权头时） | 该前缀在**另一套网关**上：只有带 `Authorization` 才会进入业务路由，鉴权失败才返回 `401 {"code":"invalid-credential"}` |
| `GET /user/billings/sessions?limit=5` | 同上 | 同上 |
| `GET /user/plans` | `200 {"code":"ok","data":[…]}` | 公开定价，无需登录（用于单价核对：`values.monthly_price` / `monthly_credits` 的单位分别是**分**与**积分**） |
| `GET /api/user/*` | `401 Request denied by JWT Auth check. JWT is missing.` | 存在 `/api` 前缀的镜像网关，用户态请求同样需要 JWT |
| `GET /biz/user/v1/settings/enterprise/quota` | `401 {"error":"Unauthorized","code":"authentication_required"}` | 企业配额另一套鉴权，本轮不接 |

3. **鉴权形态**：前端请求统一 `withCredentials: true`，`/user/*`、`/auth/*`、`/biz/*` 走浏览器 Cookie 会话（`index-Dm_Kd17d.js` 的 `Xe()` 与 axios 实例配置）；只有 `VITE_DEV_JWT`（开发注入，生产为空）才会额外加 `Authorization: Bearer`。因此**适配器持网页登录态 Cookie 即可**，不需要单独抓令牌——这与小浣熊（令牌在 Cookie 里、必须转成 Bearer）不同。

> 待确认：`/user/billings/expirations` 与 `/user/billings/sessions` 在**带真实 Cookie** 时的完整返回体（尤其 `expirations` 的条目字段名）尚未实测；适配器对二者都按「字段缺失即降级」处理，不把缺失当成 0。

## 3. 方案设计

### 3.1 整体思路

**新增 `qwenwork` 适配器，凭证只有「网页登录态 Cookie」（必填），沿用 `xiaohuanxiong.ts` 的骨架：信封解包 → 余额 → 明细 → 订阅信息 → 组装批次。**

```
qwenwork.cn 网页端
   │  Cookie（登录态，浏览器会话）
   ▼
src/providers/qwenwork.ts  probe()
   ├── GET /user/balance        → balance（可用总额）
   ├── GET /user/wallets        → daily_credits / monthly_credits / longterm_credits
   ├── GET /user/info           → 昵称（仅占位名时补查）+ 登录判据
   └── GET /user/billings       → 逐笔流水（分页，fetchAllPages）
        ▼
   CreditLot[]（daily / monthly / longterm）+ windows[]（无）
        ▼
src/service.ts 并发与缓存 → src/aggregate.ts 聚合 → /api/summary
        ▼
public/app.js 卡片 / 到期时间线（完全按适配器声明渲染，前端无需改动）
```

### 3.2 职责划分

| 层 | 文件 | 职责 |
| --- | --- | --- |
| 适配器层 | `src/providers/qwenwork.ts`（新增） | 凭证解析、请求与信封校验、三桶解析、批次构建、用量明细 |
| 注册/别名 | `src/providers/index.ts` | 注册 `qwenworkAdapter` + 域名别名 |
| 抓取 | `src/cli/capture.ts` | 新增 `Target`（Cookie 平台，无令牌字段） |
| 估值 | `src/credit-value.ts` | 新增 `qwenwork` 的 `CREDIT_PEG` |
| 编排/聚合/前端 | `src/service.ts`、`src/aggregate.ts`、`public/app.js` | **不改**（全部声明驱动） |

## 4. 接口设计

### 4.1 上游接口（适配器消费）

| 接口 | 方法 | 关键入参 | 关键出参 | 用途 |
| --- | --- | --- | --- | --- |
| `/user/balance` | GET | — | `{ balance }` | 账户级可用积分 |
| `/user/wallets` | GET | — | `{ balance, daily_credits{total_balance}, monthly_credits{total_balance}, longterm_credits{total_balance} }` | 三桶构成 |
| `/user/info` | GET | — | `{ nickname, username, email, avatar, plan{pid,name,next_due_date,next_refresh_date,subscription_status}, is_biz }` | 昵称 + 套餐 + 订阅到期 |
| `/user/billings` | GET | `limit`、`cursor`、`source=all` | `{ items[{amount, created_at, detail{title}, transaction_id}], has_more, next_cursor, total_pages }` | 逐笔用量 |
| `/user/billings/expirations` | GET | `limit`、`cursor` | `{ items[], has_more, next_cursor }` | **仅诊断用**：本轮不消费（见 §5.4） |

请求头：`Accept: application/json`、浏览器 UA（复用 `fetchJson` 的默认 UA / `HTTP_USER_AGENT`）、`Referer: https://qwenwork.cn/app/settings/usage`（前端同源请求自带；服务端补上更贴近真实流量）、`Cookie: <登录态>`。

错误映射：HTTP 401/403 → `unauthorized` / `forbidden`；信封 `code !== 'ok'` → 抛错（`msg` 原样带出）；`code === 'invalid-credential'` 归为登录态失效。

### 4.2 适配器契约

```ts
export const qwenworkAdapter: ProviderAdapter = {
  id: 'qwenwork',
  displayName: '千问办公',
  region: 'cn',
  dashboardUrl: QWENWORK_USAGE_URL,
  usageUrl: QWENWORK_USAGE_URL,
  requiredCredentialKeys: ['cookie'],
  envNames: { cookie: 'QWENWORK_COOKIE' },
  credentialHint: '…',
  manageAccounts: true,
  manageFields: [{ key: 'cookie', label: 'Cookie', multiline: true, hint: '需含登录态 Cookie' }],
  login: qwenWorkWebLogin,       // 网页端登录（CDP）
  loginMethods: [qwenWorkWebLogin],
  fetchUsageLedger(...),         // 逐笔流水 → UsageRecord[]
  probe(...),
};
```

`options` 支持：

| 键 | 含义 | 默认 |
| --- | --- | --- |
| `origin` | 覆盖站点（代理 / 测试环境） | `https://qwenwork.cn` |
| `orgId` / `corpId` | 企业组织上下文（上游请求头 `X-Org-Id` 类参数的原型）；**本轮不主动发**，仅记录在 options 以便排查 | 空 |

## 5. 数据模型

### 5.1 `types.ts` 契约变更

**无变更**。三桶全部落成既有 `CreditLot`：

| 批次 id | label | amount 来源 | currency | expiresAt | basis |
| --- | --- | --- | --- | --- | --- |
| `qwenwork-daily` | 每日刷新积分 | `daily_credits.total_balance` | CREDITS | 北京时间当日 24:00（上游不给明细到期时） | remaining |
| `qwenwork-monthly` | 每月订阅积分 | `monthly_credits.total_balance` | CREDITS | `plan.next_refresh_date` → 兜底 `plan.next_due_date` | remaining |
| `qwenwork-longterm` | 长期积分 | `longterm_credits.total_balance` | CREDITS | `null`（上游未给批次级到期；「有效期以具体规则为准」⇒ 不给假标签、不参与「最快到期」） | remaining |

`balance.amount` 取 `/user/balance` 的 `balance`（平台自己显示的「剩余可用」），`currency: 'CREDITS'`。

### 5.2 配置项

`.env` 新增：`QWENWORK_COOKIE`（唯一变量，多账号为 `QWENWORK_COOKIE_2` …）。

`accounts.json` 新增示例条目：

```json
{
  "provider": "qwenwork",
  "displayName": "千问办公",
  "enabled": false,
  "credentials": { "cookie": "${QWENWORK_COOKIE}" },
  "options": {}
}
```

无配置迁移（从零新增）。

### 5.3 缓存语义

沿用编排层：`CACHE_TTL_SECONDS`（默认 300s）内命中缓存；`accounts.json` / `.env` mtime 变化触发热加载并失效缓存。适配器自身不缓存（无令牌续期需求，Cookie 由用户 / capture 更新）。

### 5.4 口径决策

| 决策 | 取值 | 理由 |
| --- | --- | --- |
| 余额主数字 | `/user/balance` 的 `balance` | 页面「剩余可用」用的就是它；三个桶是它的构成 |
| 三桶之和 ≠ balance | 照常展示桶，note 里写明差额 | 可能有一类未入桶（企业共享 / 试算），如实说明比静默改数安全 |
| 每日桶到期 | 北京时间当日 24:00 | 上游文案「每天 00:00 刷新」；不跟随容器时区 |
| 每月桶到期 | `plan.next_refresh_date` → `plan.next_due_date` → 北京时间本月末（**只接受未来时间**，已是过去的旧值会被跳过，避免把仍有余额的桶判成已过期） | 页面「下次刷新时间」用的就是前者；后两级是上游缺字段时的兜底，其中第三级会在 note 里注明「推算」 |
| 长期桶到期 | 不填（`null`） | 「有效期以具体规则为准」＝平台不保证；`/user/billings/expirations` 只给「已过期」记录，推不出「当前批次的到期时间」，没有证据就不标日期 |
| 过期积分接口 | 本轮不消费 `/user/billings/expirations` | 它返回的是**已过期**记录，用于展示历史；不影响当前余额与「最快到期」 |

### 6.1 人民币估值口径

平台的公开定价（`GET /user/plans`，2026-10-27 查证）给出「每月固定通用积分 + 月租」：

| 套餐 | 每月积分 | 月租 | 折合 |
| --- | --- | --- | --- |
| 个人基础版（`qwen-office-basic`） | 200 | ¥22.40（原价 ¥28.00） | ¥0.112 / 积分 |
| 个人标准版（`qwen-office-plus`） | 2,000 | ¥78.00 | ¥0.039 / 积分 |
| 个人高级版（`qwen-office-pro`） | 4,000 | ¥158.00 | ¥0.0395 / 积分 |
| 企业基础版（`qwen-office-enterprise`） | 2,000 / 席 | ¥198.00 / 席 | ¥0.099 / 积分 |

采用**标准版 2,000 积分 / ¥78**＝`¥0.039/积分` 作为官方口径（与 Qoder CN 的 ¥0.0295、CodeBuddy 的 ¥0.05 同一量级，且是该平台最常被购买的个人付费档）。
DeepSeek 基准：平台未公布「1 积分 = 多少 token / 某模型系数」，与 Qoder / CodeBuddy 同属「缺一环」，`flashRatio: null`，悬停里写明缺哪一环。

## 7. 风险与备选方案

| 风险 | 等级 | 应对 |
| --- | --- | --- |
| `/user/billings` 在真实登录态下分页参数名不同（`cursor` vs `page`） | 中 | 先用 `cursor`；`fetchAllPages` 的 `complete` 为 false 时整份退回本地采样，并在 note 明写「未取全」，不把截断值当完整值 |
| 网页 Cookie 会话寿命短（阿里云系常见数小时） | 中 | 401 时快照给 `unauthorized` + 明确文案；推荐 `npm run capture -- qwenwork` 重抓；不做伪自动续期（无公开刷新端点） |
| 三桶字段名改版（`daily_credits` 等） | 低 | 解析时用 `pick` 兼容 camelCase；字段整体缺失时退回「只有总额」并 note 说明 |
| 企业版账号口径不同 | 低 | `is_biz === true` 时 note 里写明「企业账号，个人积分仍按三桶展示，企业配额未纳入」 |
| 上游 WAF 校验 UA / Referer | 低 | 复用 `fetchJson` 的 UA（可由 `HTTP_USER_AGENT` 覆盖）+ 固定 Referer |

**被否决的备选**：

1. *只显示总额（一条 lot）*：丢失「哪桶先过期」，正是看板的核心价值。
2. *把每日积分按 24:00 强行写成所有桶的到期*：会给每月 / 长期积分标错误的日期，违反「没有证据不猜」。
3. *接企业配额接口*：鉴权与企业上下文（`X-Org-Id`、成员维度）是另一套，本轮不扩大范围。
