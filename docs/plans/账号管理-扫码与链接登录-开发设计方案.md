## 1. 背景与目标

**结论**：把 CodeBuddy、Qoder、Trae 三个平台的「添加账号」从「手工粘贴 Cookie」升级为「扫码或打开链接登录，授权后自动落库」，并保持现有「一个账号一张卡片」的展示与增删语义不变。登录是**新增入口**，不是替换：手工 Cookie 方式继续保留，作为协议漂移时的兜底。

### 1.1 要解决的问题

| 编号 | 问题 | 现状证据 |
| --- | --- | --- |
| P1 | 添加账号要求用户会开 DevTools 复制 Cookie | `src/providers/codebuddy.ts:178-187`、`src/providers/qoder.ts:519-537` 的 `manageFields` 只有一个 Cookie 输入框 |
| P2 | Cookie 会过期，过期后只能重新抓 | `src/providers/trae.ts:183-221` 用 Cookie 换 JWT；Cookie 失效时整张卡片报错 |
| P3 | 用户已经有官方客户端登录态，却要再手工搬一次 | 三平台都有可复用的官方登录协议（见 §2.4） |
| P4 | Trae 目前没有看板增删入口 | `src/providers/trae.ts:225-245` 未声明 `manageAccounts` |
| P5 | 登录产物是令牌而非 Cookie，现有适配器只认 Cookie | `codebuddy.ts:163`、`qoder.ts:512`、`trae.ts:231` 的 `requiredCredentialKeys: ['cookie']` |

### 1.2 目标

1. **三个平台各有一套登录入口**：卡片上的「＋ 添加账号」展开后，优先展示「扫码 / 打开链接登录」，手工 Cookie 折叠为兜底。
2. **服务端完成协议交互**：二维码只承载 `authUrl`；授权轮询在服务端后台进行，不依赖浏览器定时器（后台标签页会被节流）。
3. **授权后自动落库**：令牌先经适配器 `probe()` 真实验证，再写入 `.env`（0600）+ `accounts.json`（只存 `${VAR}` 引用），写入前备份到 `.run/`。
4. **一个账号一张卡片**：三个平台都不声明 `groupAccounts`；同一平台账号重复登录时按平台账号 ID **更新原条目**，不新增卡片。
5. **令牌可续期**：CodeBuddy / Qoder / Trae 的 refresh token 在探测失败时自动刷新，并把新令牌写回 `.env`。
6. **不引入运行时依赖**：二维码用本地内置的 MIT 单文件编码器（`public/vendor/`），`package.json` 依赖不变。

### 1.3 Non-Goals（明确不做）

- **不做 CodeBuddy 国际站（WorkBuddy）登录**：本仓库的 CodeBuddy 卡片面向 `www.codebuddy.cn`；国际站登录协议虽同源，但计费域与账号体系不同，v1 不开放。
- **不做 Qoder 国际站登录**：设备流的国际站 openapi 主机未经验证（见 §2.4.2 的「待确认」），v1 仅支持国内站；国际站继续用 Cookie。
- **不做 Trae 手机扫码**：Trae 是 OAuth 本地回调（`http://127.0.0.1:<port>/authorize`），手机扫码后回调会落到手机自己身上，必然失败；Trae 只提供「打开链接登录」，并要求看板与服务在同一台机器上打开。
- **不做浏览器自动化 / 内嵌 WebView**：不引入 Playwright、不启动调试 Chrome；登录完全走协议。
- **不改变现有 Cookie 取数口径**：CodeBuddy/Qoder 的 Cookie 路径、Trae 的 Cookie 换 JWT 路径保持原样。
- **不做账号合并卡片**：不声明 `groupAccounts`（合并会清空 `credits/windows/nextExpiryAt`，见 `src/aggregate.ts:97-110`）。
- **不自动迁移已有 Cookie 账号**：登录账号与 Cookie 账号是两条独立条目；用户可自行删除旧条目。

### 2.4 三平台登录协议调研结论

#### 2.4.1 CodeBuddy（腾讯插件认证，扫码可行）

| 步骤 | 请求 | 关键字段 |
| --- | --- | --- |
| ① 申请 state | `POST https://copilot.tencent.com/v2/plugin/auth/state?platform=CLI`，body `{}` | 响应 `data.state`、`data.authUrl` |
| ② 轮询令牌 | `GET https://copilot.tencent.com/v2/plugin/auth/token?state=<state>` | `data.accessToken`、`refreshToken`、`expiresIn`、`domain`；无 token 即等待 |
| ③ 取账号 | `GET https://copilot.tencent.com/v2/plugin/login/account?state=<state>`，`Authorization: Bearer <accessToken>` | `data.uid`、`nickname`、`enterpriseId` |
| ④ 刷新 | `POST https://copilot.tencent.com/v2/plugin/auth/token/refresh`，`X-Refresh-Token` 头 | `accessToken`、`refreshToken`、`expiresIn`、`domain` |
| ⑤ 查积分 | `POST https://www.codebuddy.cn/v2/billing/meter/get-user-resource` | `Accounts[].CycleCapacitySize/Remain/Used`、`CycleEndTime` |

- **可行性**：workbuddy 已用同一套腾讯后端验证过；CN 的 `chat_base = https://copilot.tencent.com`、`billing_base = https://www.codebuddy.cn`（`workbuddy-manager/server/config.py:152-153`）。
- **扫码**：`authUrl` 是网页授权页，手机扫码登录后服务端轮询即可拿到 token，扫码可行。
- **待确认**：CN CodeBuddy 插件登录的出站 UA 是否必须为 `WorkBuddy/...` 形态。v1 先复用 workbuddy 已验证的 UA（`WorkBuddy/<ver> ... CLI/<ver>`），失败时可用 `HTTP_USER_AGENT` 覆盖。

#### 2.4.2 Qoder（设备流，扫码可行）

从 `qodercli 1.1.63` 二进制中提取的设备流（`startDeviceFlow`）：

```
authUrl = {website}/device/selectAccounts?
            challenge=<S256(verifier)>&challenge_method=S256&nonce=<uuid>
            &machine_id=<id>&client_id=e883ade2-e6e3-4d6d-adf7-f92ceff5fdcb
poll    = GET {openapi}/api/v1/deviceToken/poll?
            nonce=<uuid>&verifier=<verifier>&challenge_method=S256
          → 404 = 等待；1s 间隔；300s 超时
          → { token, refresh_token, user_id, user_name, expires_at, ... }
refresh = POST {openapi}/api/v1/deviceToken/refresh
          body { refresh_token, machine_id? }
```

| 项 | 值 | 证据 |
| --- | --- | --- |
| 国内站网页 | `https://qoder.com.cn` | `qodercli` 配置表；`src/providers/qoder.ts:93-100` |
| 国内站 openapi | `https://openapi.qoder.com.cn` | `qodercli` 配置表；`QoderBridge/src/qoder/endpoints.ts:16` |
| 生产 client_id | `e883ade2-e6e3-4d6d-adf7-f92ceff5fdcb` | `qodercli` `startDeviceFlow` |
| PKCE | verifier 43–128 字符，challenge = base64url(sha256(verifier)) | `qodercli` `A()` |
| 业务面鉴权 | 仅 `Authorization: Bearer` + `Accept: application/json`，**禁止** `cosy-*` 头 | `qodercli` `getBearerToken`；`QoderBridge/docs/协议参考.md:13-21` |

- **可行**：设备流就是为「浏览器登录、客户端轮询」设计的，扫码可行。
- **取舍（重要）**：设备 token 只能走 openapi `/api/v2/quota/usage`，该接口返回 `userQuota/addOnQuota/isQuotaExceeded/totalUsagePercentage`，**不返回批次到期时间**（`QoderBridge/src/qoder/auth.ts:256-299`）。现有 Cookie 路径的 `quota_detail[].expires_at` 才有批次到期。
- **用户确认（2026-10-18）**：令牌探测**先尝试**用 `Authorization: Bearer` 访问现有网页用量接口 `/api/v2/me/usages/big_model_credits`；能解析出 `total_quota` 就沿用现有解析（含批次到期），失败再退回 openapi `/api/v2/quota/usage`（无批次，note 说明）。这样既不放弃批次到期，也不阻塞登录。
- **待确认**：国际站设备流主机（`qoder.com` / `openapi.qoder.com`）是否可用；`/api/v2/user/plan` 是否返回本期重置时间。v1 登录仅支持国内站。

#### 2.4.3 Trae（OAuth + 本地回调，扫码不可行）

从 `Trae CN 1.107.1` 的 `out/main.js` 提取：

| 步骤 | 实现 | 关键点 |
| --- | --- | --- |
| ① 登录 URL | `buildLoginUrl()` | `{consoleHost}/authorization?login_version=1&auth_from=trae&login_channel=native_ide&plugin_version=<ver>&auth_type=local&client_id=ono9krqynydwx5&redirect=0&login_trace_id=<uuid>&auth_callback_url=http://127.0.0.1:<port>/authorize&machine_id=<id>&device_id=<uuid>&code_challenge=<S256>&code_challenge_method=S256` |
| ② 本地回调 | `OAuthLocalServer` | 只监听 `/authorize`；从 query 取 `userJwt`、`authCodeInfo`、`host`、`consoleHost` |
| ③ 换令牌 | `exchangeTokenByAuthCode()` | `POST {apiHost}/trae/api/v3/oauth/ExchangeToken`，body `{ClientID, AuthCode, CodeVerifier, DeviceInfo, IDEVersion}`；**不需要** DeviceProof |
| ④ 取用户 | `getUserInfo()` | `POST {apiHost}/cloudide/api/v3/trae/GetUserInfo`，头 `x-cloudide-token` |
| ⑤ 刷新 | `exchangeTokenByRefreshToken()` | 同一 ExchangeToken 端点，body 带 `RefreshToken` + `DeviceProof{Signature,Timestamp,Nonce}`；签名内容 `[method, path, clientId, refreshToken, timestamp, nonce].join('\n')` |
| 设备密钥 | `Oxe()` | `generateKeyPairSync('ec', {namedCurve:'P-256', spki/pkcs8 PEM})`；`DeviceInfo.DevicePublicKey` 用公钥 PEM |

- **可行性**：Node 原生 `crypto` 可完整复刻（EC P-256、ECDSA-SHA256、PKCE），零依赖。
- **扫码不可行**：回调固定落到 `127.0.0.1`，手机扫码后回调会打到手机自己。v1 只提供「打开链接登录」，并在前端提示必须在本机打开。
- **待确认**：`GetUserInfo` 返回结构（`Result.Data.UserInfo.UserID/ScreenName`）与刷新请求是否需要 `x-cloudide-token` 头；`authCodeInfo` 在回调中的编码形式（JSON 或 URL 编码 JSON，两种都兼容）。

## 3. 方案设计

### 3.1 总体思路

**结论**：在 `ProviderAdapter` 上增加一个可选的 `login` 能力声明；新增一个平台无关的**登录会话层**（`src/login-session.ts`）负责状态机、后台轮询与落库；三个适配器各自实现协议细节。前端只按 `/api/providers` 下发的 `login` 元信息渲染入口，不认平台名。

```
用户点击「扫码 / 打开链接登录」
  → POST /api/login/start
  → adapter.login.start() 申请 authUrl（CodeBuddy state / Qoder 设备流 / Trae OAuth）
  → 服务端建会话，后台按适配器间隔轮询上游
前端每 2s GET /api/login/poll
  → waiting / ready / expired / failed
ready 时服务端已把令牌经 probe() 验证并落库
  → 前端刷新看板，出现/更新对应卡片
```

### 3.2 数据流

```
上游授权页 ──(用户扫码/登录)──▶ 上游令牌接口
                                   ▲
                                   │ 服务端后台轮询
┌──────────────┐   start/poll   ┌──┴──────────────┐
│ public/app.js│ ─────────────▶ │ src/server.ts   │
│ 登录弹窗      │ ◀───────────── │ /api/login/*    │
└──────────────┘  仅状态/掩码    └──┬──────────────┘
                                    │
                          ┌─────────▼──────────┐
                          │ src/login-session  │
                          │ 会话状态机 + 落库   │
                          └─────────┬──────────┘
                                    │ addManagedAccount / updateManagedAccount
                          ┌─────────▼──────────┐
                          │ src/account-store  │
                          │ probe → 去重 → 槽位 │
                          └─────────┬──────────┘
                                    │
                          .env(0600) + accounts.json
                                    │ mtime 热加载
                          ┌─────────▼──────────┐
                          │ src/service.ts     │
                          │ 一账号一卡片        │
                          └────────────────────┘
```

### 3.3 职责划分

| 层 | 文件 | 职责 |
| --- | --- | --- |
| 契约层 | `src/providers/base.ts` | `login?: ProviderLogin`、`isConfigured?`、`ProbeContext.persistCredentials?` |
| 协议层 | `src/providers/codebuddy.ts` / `qoder.ts` / `trae.ts` | 各自的 `login.start/poll`、令牌探测、刷新、身份字段 |
| 会话层 | `src/login-session.ts`（新增） | 会话表、TTL、后台轮询、取消、终态缓存、回调投递 |
| 存储层 | `src/account-store.ts` | 新增 `updateManagedAccount()`；`addManagedAccount()` 支持 `internalOptions`；`complete` 改用 `isConfigured` |
| 编排层 | `src/service.ts` | 给 `ProbeContext` 注入 `persistCredentials`（令牌刷新写回） |
| 接口层 | `src/server.ts` | `/api/login/start|poll|cancel`、Trae `/authorize` 回调 |
| 前端 | `public/app.js` / `index.html` / `styles.css` | 登录入口、弹窗、二维码、轮询、结果提示 |
| 二维码 | `public/vendor/qrcode.js`（新增） | MIT 编码器，前端本地渲染，不上传 authUrl |

### 3.4 登录会话状态机

```
start ──▶ waiting ──(上游返回令牌)──▶ landing ──(probe 通过 + 落库)──▶ ready
             │                           │
             │                           └─(probe/写入失败)──▶ failed
             ├─(超过 TTL)──▶ expired
             └─(用户取消 / 同平台重新发起)──▶ cancelled
```

| 状态 | 前端文案 | 是否终态 |
| --- | --- | --- |
| `waiting` | 等待扫码 / 等待授权… | 否 |
| `ready` | 已添加「X」/ 已更新「X」 | 是 |
| `expired` | 二维码已过期，请重新获取 | 是 |
| `failed` | 登录失败：<可操作原因> | 是 |
| `cancelled` | 已取消 | 是 |
| `invalid` | 会话不存在或已清理 | 是 |

- **TTL**：CodeBuddy 900s（对齐 workbuddy `STATE_TTL`）；Qoder 300s（对齐 qodercli）；Trae 300s（对齐 IDE 的 5 分钟回调超时）。
- **后台轮询**：`start` 后立即启动，不依赖前端；前端只读本地状态。
- **终态缓存**：终态保留到 TTL 结束，重复 `poll` 直接返回，避免重复落库。
- **单平台单会话**：同一 provider 再次 `start` 会取消旧会话（旧二维码随即失效），避免多个 state 混淆。
- **不落日志的内容**：令牌、refresh token、authUrl 全文、PKCE verifier、设备私钥。

### 3.5 三平台适配器改造

#### 3.5.1 CodeBuddy

| 项 | 设计 |
| --- | --- |
| 新凭证 | `accessToken`、`refreshToken` |
| 新 options | `uid`、`enterpriseId`、`domain`、`realm`（v1 固定 `cn`）、`loginAccountId`、`loginName` |
| `isConfigured` | 有 `cookie`，或同时有 `accessToken` + `refreshToken` |
| `probe` 分支 | 有 Cookie → 现有路径不变；否则走令牌路径 |
| 令牌探测 | `POST {billing_base}/v2/billing/meter/get-user-resource`，Bearer + 身份头；解析 `Accounts[]` |
| 刷新时机 | HTTP 401/403，或业务 `code=12153`（登录态失效）时刷新一次并重试 |
| 刷新写回 | `ctx.persistCredentials({ accessToken, refreshToken })` |
| 用量明细 | 令牌模式与 Cookie 模式同源：`get-user-request-usage`（Bearer + `X-Client-Platform: web`，插件后端优先、网页域 404/401 回退）+ 资源包发放（同一 `get-user-resource`）+ 礼包；2026-10-18 修复，见 `docs/fixes/CodeBuddy-令牌模式用量明细失效-修复方案.md` |
| 卡片 note | 令牌模式注明「登录令牌模式，用量/获取明细取自同一令牌的网页域接口」 |

**令牌探测的积分口径**（对齐 `tencent.py:875-919`）：

```
remain(item) = CycleCapacitySize > 0
  ? clamp(CycleCapacityRemain, 0, CycleCapacitySize)   // 再用 CycleCapacityUsed 反修正
  : CapacityRemain
expiry(item) = parseUtc8(CycleEndTime)                  // 'YYYY-MM-DD HH:mm:ss'，显式 +08:00
balance = Σ max(0, remain)
limit   = Σ max(0, CycleCapacitySize ?? CapacitySize)
used    = max(0, limit - balance)
credits = 每个 remain>0 的套餐 → CreditLot(expiresAt)
```

### 3.6 Trae 登录回调设计

**结论**：回调复用主服务端口，不额外监听端口；回调 URL 必须是**裸** `http://127.0.0.1:<PORT>/authorize`，会话由活跃会话反查（原 `?lt=` 方案已被上游正则校验否决，见 `docs/fixes/Trae-打开链接登录网络错误-修复方案.md`）。

1. `start` 生成 `traceId = randomUUID()`、`verifier/challenge`、EC P-256 密钥对、`deviceId`、`machineId`。
2. `auth_callback_url = http://127.0.0.1:<PORT>/authorize`（`<PORT>` 取 `config.server.port`）。Trae 授权页用 `^http://127\.0\.0\.1:(\d+)/authorize$` 严格校验，任何查询串都会进入「登录失败 / 网络错误」。
3. 登录 URL 按 §2.4.3 拼接，`code_challenge` 用本地 verifier。
4. 用户在浏览器完成登录后，Trae 把 `authCodeInfo` / `userJwt` / `host` / `consoleHost` 追加到回调 URL。
5. `GET /authorize`：
   - 只接受回环 Host（与 `privilegedGuard` 的回环判断同源）；
   - 用 `lt` 找会话，找不到返回 404；
   - 校验 `host` 的 hostname 属于 `trae.cn` / `trae.com.cn`（或会话登记的 console host），否则拒绝，避免 SSRF/令牌外送；
   - 把 query 存入会话，返回一个静态「登录完成，请回到看板」页面（不包含任何令牌）。
6. 后台轮询看到回调后：`ExchangeToken` → `GetUserInfo` → `ready`。

**限制**：看板必须在服务所在机器上通过 `127.0.0.1` / `localhost` 打开；从其他机器打开时前端会提示改用 Cookie 方式。

### 3.7 二维码实现（零依赖）

**结论**：内置 MIT 单文件编码器到 `public/vendor/qrcode.js`，前端本地渲染；不调用任何在线二维码服务（authUrl 含 state/challenge，不能外送）。

| 项 | 说明 |
| --- | --- |
| 来源 | `qrcode-terminal@0.12.0` 内置的 `vendor/QRCode/*`（Kazuhiko Arase，MIT，10 个 CommonJS 文件） |
| 改造 | 合并为单个 ES module/IIFE，保留原 MIT 头与来源说明；`public/vendor/README.md` 记录版本、许可、改造点 |
| 渲染 | `qrcode(0, 'M')` 自动选版本 → `addData(authUrl)` → `make()` → 画到 `<canvas>`（含 4 模块静区） |
| 失败降级 | URL 过长或编码失败时隐藏二维码，只显示可点击链接 + 复制按钮 |
| 依赖约束 | 只进 `public/`，不进 `package.json`；运行时仍零 npm 依赖 |

### 4.2 HTTP API

所有 `/api/login/*` 都走 `privilegedGuard`（回环 + Origin + `X-Power-Meter-Intent`）。

**实际接口（与实现一致，2026-10-18 回填）**：

| 方法 | 路径 | 入参 | 出参 |
| --- | --- | --- | --- |
| POST | `/api/login/start` | `{ provider: string, options?: Record<string,string> }` | `{ ok: true, session: LoginSessionView }` |
| GET | `/api/login/poll?id=` | — | `{ ok: true, session: LoginSessionView }` |
| POST | `/api/login/cancel` | `{ id }` | `{ ok: true, session: LoginSessionView }` |
| GET | `/authorize?lt=&...` | Trae 回调 query | HTML（成功/失败提示，无令牌） |

`LoginSessionView`：`{ id, provider, status, authUrl, qr, hint, message, createdAt, expiresAt, account: { name, updated } | null }`；
`authUrl` 只在 `waiting` / `landing` 阶段下发，终态后为 `null`。

错误码：

| 状态 | 场景 |
| --- | --- |
| 403 | 非本机来源、Origin 非回环、缺 intent 头；平台未声明 `login` |
| 404 | `provider` 未知、`id` 不存在或已清理、Trae 回调找不到会话 |
| 502 | 上游申请 authUrl 失败（附上游 code/message，不含令牌） |

> 方案原稿里的 `400`（缺 provider）与 `409`（同平台已有会话）未采用：缺 provider 走 404；
> 同平台再次 `start` 直接取消旧会话（`cancelled`），前端只保留最新二维码。

**安全约束**：

- 响应里永远不出现 accessToken / refreshToken / deviceKey / verifier。
- `authUrl` 只返回给发起登录的页面；日志不打印全文。
- `/authorize` 不经过 `privilegedGuard`，但有回环 Host 校验、`lt` 会话绑定、Trae 域名校验。

### 4.3 CLI（本期不做）

`npm run account` 保持现状（`src/cli/account.ts:79-90` 只列 `manageAccounts + manageFields` 的平台）。登录是交互式流程，CLI 里做二维码体验差；后续如需，可加 `npm run login -- <provider>` 打印 authUrl。**本期 Non-Goal。**

| 平台 | credentials 新键 | options 新键 | 身份键（去重用） |
| --- | --- | --- | --- |
| CodeBuddy | `accessToken`、`refreshToken` | `realm`、`uid`、`enterpriseId`、`domain`、`loginAccountId`、`loginName` | `loginAccountId` = uid |
| Qoder | `accessToken`、`refreshToken` | `site`、`userId`、`loginAccountId`、`loginName` | `loginAccountId` = user_id |

### 5.2 .env

| 平台 | 新增变量 | 说明 |
| --- | --- | --- |
| CodeBuddy | `CODEBUDDY_ACCESS_TOKEN`、`CODEBUDDY_REFRESH_TOKEN` | 第 2 个登录账号自动用 `_2` 槽位 |
| Qoder | `QODER_ACCESS_TOKEN`、`QODER_REFRESH_TOKEN` | 同上 |
| Trae | `TRAE_ACCESS_TOKEN`（复用现有键）、`TRAE_REFRESH_TOKEN`、`TRAE_DEVICE_KEY` | `TRAE_DEVICE_KEY` 存 PKCS8 PEM 的 base64（`.env` 不能放多行） |

- 写入权限 0600；写入前备份到 `.run/`（仅登录落库/更新时，例行刷新不备份）。
- 刷新写回：读 `.env` → 改对应变量 → 临时文件 + rename（失败回退直接写）→ `loadDotEnv()` 同步 `process.env`；所有写操作串行化，避免并发读改写丢更新。
- 若账号的凭证是明文直填（不是 `${VAR}`），刷新时不改写明文，只记一条日志；下次探测会再次刷新。
- `.env.example` 只加注释占位符，不写真实值。

### 5.3 内存会话

| 字段 | 说明 |
| --- | --- |
| `id` | `randomUUID()`，前端轮询键 |
| `provider` | 适配器 id |
| `phase` | `waiting/ready/expired/failed/cancelled` |
| `authUrl` / `qr` | 前端展示用 |
| `expiresAt` | 会话 TTL |
| `secret` | 协议私有状态（state/verifier/密钥/回调 query） |

### 5.4 迁移

- **无破坏性迁移**：现有 `accounts.json` / `.env` 不改；Cookie 账号照常工作。
- 新增字段全部可选；旧版本代码读到未知 `options` 会原样保留（`config.ts` 的 `expandDeep` 不丢键）。
- 回滚：删除登录条目 + 删除新增 `.env` 变量即可；Cookie 条目不受影响。

| 影响点 | 说明 | 风险等级 |
| --- | --- | --- |
| `ProviderAdapter` 扩展 | 全部可选；未声明 `login` / `isConfigured` 的适配器行为不变 | 低 |

## 7. 风险与备选方案

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 三平台协议均为逆向所得，上游改版 | 登录失败 | 常量集中在一个文件；错误信息带 HTTP 状态与上游 code；Cookie 手工入口始终保留 |
| CodeBuddy 插件登录 UA/风控 | 申请 state 或轮询被拒 | 复用 workbuddy 已验证的 UA 与身份头；支持 `HTTP_USER_AGENT` 覆盖；失败提示改用 Cookie |
| Qoder 令牌模式丢失批次到期 | 「最快到期」少一个账号 | 卡片 note 明示；登录弹窗提前说明；需要批次到期的用户用 Cookie |
| Trae 回调端口/回环限制 | 远程看板无法登录 | 前端检测非回环 host 时提示；保留 Cookie 方式 |
| Trae 设备私钥落 `.env` | 私钥泄露风险 | `.env` 0600 + gitignore；不声明 `revealableSecrets`；日志不打印 |
| 令牌刷新并发写 `.env` | 丢更新 / 文件截断 | 写操作串行化 + 临时文件 rename；刷新失败不阻断本次探测 |
| 同一账号 Cookie/登录两条记录 | 两张卡片 | 文档说明；登录按平台 ID 去重；不做自动合并 |
| 会话被遗忘 | 内存增长 | 每个 start 先 prune；终态保留到 TTL；单平台单会话 |

**备选方案与否决原因**：

| 备选 | 否决原因 |
| --- | --- |
| 用 Playwright/调试 Chrome 自动登录 | 引入运行时依赖、需要图形环境；与本仓库「零第三方依赖」冲突 |
| 二维码调用在线生成服务 | authUrl 含 state/challenge，外送等于泄露登录会话 |
| 令牌存 `.run/tokens.json` 而不是 `.env` | 需要新的存储层与列表/删除逻辑；复用现有 `.env` 槽位/备份/删除链路更稳 |
| 三个平台合并成一张卡片 | 会清空 `credits/windows/nextExpiryAt`（`src/aggregate.ts:97-110`），与「最快到期」目标冲突 |
| Trae 也做扫码 | 回调固定 127.0.0.1，手机扫码必然失败；做假扫码会误导用户 |
