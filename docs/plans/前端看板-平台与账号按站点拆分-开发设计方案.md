## 1. 背景与目标

**结论：顶栏「平台与账号」弹窗一个平台一行（`Qoder` + 「国内」标签），但从这里点「登录 / 添加账号」进去后站点只是表单里的一个下拉项，默认 `cn` 且没有任何提示——用户无法从入口本身区分「我要加的是国内版还是国际版」，也看不出已有账号各属于哪个站点。本次把弹窗按站点拆行：`Qoder 国内版` / `Qoder 国际版`，各行独立展示该站点的账号、独立带「登录 / 添加账号」入口，并且站点在添加/登录时被**锁定**为所选版本。**

### 1.1 要解决的问题

| 编号 | 现象 | 现状证据 |
| --- | --- | --- |
| P1 | 平台列表一个平台一行，站点信息只有适配器级的 `region` 徽标（Qoder 恒为「国内」），不反映账号实际站点 | `public/app.js:1751-1784`（`buildPlatformRow` 只读 `platform.region`）；`/api/accounts/overview` 返回的 `qoder.region = "cn"`（实测） |
| P2 | 账号行不带站点，看不出某账号属于哪个站点 | `src/account-store.ts:250-265`（`ManagedAccountView` 只有 id/label/enabled/complete/previews/envRefs，无 `options`） |
| P3 | 「登录 / 添加账号」进去后站点是下拉框、默认 `cn`；国际版账号必须手动改下拉，容易加错 | `public/app.js:1442-1450`（字段下拉按 `defaultValue` 选中）；`public/app.js:1196-1211`（登录站点下拉默认取 `defaultValue`） |
| P4 | 弹窗的账号清单是「整个平台」的，国内版与国际版混在一起 | `public/app.js:1638-1643`（标题写死「本平台已配置的账号」） |

### 1.2 目标

1. 平台列表按站点拆行：声明了站点选项（`manageFields` 里 `target: 'option'` 且有 `choices`）的平台，每个具体站点一行；标签与「按平台」子菜单共用同一份站点文案（`国内版` / `国际版`）。
2. 每行显示该站点自己的账号数、账号清单、删除按钮。
3. 每行独立「登录 / 添加账号」：进入后**站点锁定**为该行站点（下拉置灰），标题写清版本，避免加错站点。
4. 没有站点声明的平台（CodeBuddy / Trae / CodeArts / MiniMax / 自定义）**行为完全不变**：仍是一行、入口文案不变。
5. 站点值不是具体站点的账号（如 `auto` / 空 / 已废弃取值）单独归到「其他站点」一行，**不提供添加入口**（`auto` 是探测策略，不是登录目标——与 `public/app.js:1198-1200` 既有的登录过滤规则一致），账号仍可删除。

### 1.3 Non-Goals（明确不做）

| 不做的事 | 原因 |
| --- | --- |
| 不新增 provider id（`qoder-global`） | 沿用 `docs/plans/平台适配器-接入Qoder国际站-开发设计方案.md` §1 的否决结论 |
| 不改 `accounts.json` / `.env` 结构 | 站点已经存在 `options.site` 里，无契约变更 |
| 不改 `/api/accounts/add`、`/api/login/*` 的入参语义 | 站点本来就走 `options.site`；本次只是把它预置+锁定 |
| 不改「按平台」子菜单与卡片渲染 | 上一轮已按站点拆分（`docs/plans/前端看板-按平台筛选按站点拆分-开发设计方案.md`），本次只改弹窗 |
| 不在后端写死 `qoder` | 站点拆行由「是否声明站点选项」驱动，任何平台声明了站点字段都自动获得同一套 UI |
| 不把 `options` 里的敏感键下发给前端 | 只下发适配器显式声明为 `target: 'option'`（非敏感）的键，见 §4.1 |

### 2.2 缺口证据

`ManagedAccountView`（`src/account-store.ts:189-201`）不含站点，因此前端无法给账号分桶：

```ts
export interface ManagedAccountView {
  id: string; label: string; enabled: boolean; complete: boolean;
  previews: Record<string, string>; envRefs: string[];
}
```

实测 `/api/accounts/overview` 的 `qoder.accounts[0]` 只有 `id/label/enabled/complete/previews/envRefs`，没有 `site`；而 `qoder.manageFields` 里确实有 `site` 字段。

## 3. 方案设计

### 3.1 整体思路

```
GET /api/accounts/overview
   platforms[]: { id, displayName, region, manageFields, accounts[] }
                                                          │
        ┌─────────────────────────────────────────────────┘
        │  每个 platform 按「站点字段的 choices」拆成若干 section：
        │    siteField = manageFields 里第一个 target==='option' 且有 choices 的字段
        │    sections = choices(去掉 auto) 各一行
        │              + 若有账号的 site 不在这些取值里 → 追加「其他站点」一行（不可添加）
        │    没有 siteField → 单个 section（行为与现在完全一致）
        ▼
   buildPlatformRow(section)      ← 名称、站点徽标、N 个账号、该站点账号清单、本行登录/添加入口
        │
        ▼ 点入口
   state.dialog = { providerId, site }   ← 站点进入对话框状态
        │
        ▼
   renderPlatformManage(section)
        ├─ 标题：`Qoder 国内版` / `Qoder 国际版`
        ├─ 手工表单：站点下拉 = 该站点且 disabled（不能选错）
        ├─ 登录块：站点下拉 = 该站点且 disabled
        └─ 账号清单：只列该站点的账号
```

### 3.2 关键规则

| 规则 | 判定 | 例子 |
| --- | --- | --- |
| 是否拆行 | 平台 `manageFields` 里有 `target: 'option'` 且 `choices` 非空的字段 | Qoder（`site`）→ 拆；CodeBuddy → 不拆 |
| 拆哪几行 | `choices` 去掉 `auto`，每个取值一行，顺序同声明顺序 | `cn` → `Qoder 国内版`；`global` → `Qoder 国际版` |
| 行标签 | `siteFilterTerm(platform.displayName, site)` —— 与「按平台」子菜单同一个函数 | `Qoder 国内版` |
| 账号归行 | 按 `account.options.site` 精确匹配；空/未声明视为不匹配 | `site: 'cn'` → 国内版行 |
| 其他站点行 | 只在该平台确实存在不匹配的账号时出现，标签 `<平台> 其他站点`，列出这些账号与它们的原始 `site` 值，**不给添加入口** | 历史 `auto` 账号 |
| 行数兜底 | 拆行时若某站点一个账号都没有，**仍然显示该行**（0 个账号） | 只有国内版账号时，国际版行仍可见 → 才能从这里添加国际版 |
| 旧后端降级 | 账号条目没有 `options` 字段（服务未重启、后端还是旧版）时**不拆行**，退回一行 | 否则所有账号会全落进「其他站点」，比不拆更误导 |
| 站点锁定 | 进入管理视图后站点下拉 `disabled` + 值预置，用户无法改成另一站点 | 防止「点国际版入口却加进国内版」 |
| 不泄露选项值 | 只下发 `manageFields` 里声明为 `target: 'option'` 的键 | `options.origin`（自定义域名）不在声明里 → 不下发 |

### 3.3 职责划分

| 单元 | 职责 | 位置 |
| --- | --- | --- |
| `ManagedAccountView.options` | 账号的非敏感选项（仅声明过的 option 字段） | `src/account-store.ts` |
| `siteFieldOf(platform)` | 取平台的站点字段声明 | `public/app.js` |
| `platformSections(platform)` | 拆出 section 列表（含账号分桶） | `public/app.js` |
| `buildPlatformRow(section)` | 渲染一行 | `public/app.js:1751` |
| `renderPlatformManage(section)` | 管理视图（标题/表单/登录站点锁定） | `public/app.js:1813` |
| `renderManage` / `renderLogin` | 接受 `target.siteScope`，预置+置灰站点 | `public/app.js:1367` / `:1076` |
| `state.dialog` | 增 `site` 维度 | `public/app.js:104` |

## 6. 影响面评估

| 影响点 | 变化 | 说明 |
| --- | --- | --- |
| 平台列表行数 | Qoder 由 1 行变 2 行（国内版 / 国际版） | 其它平台行数不变 |
| 平台计数 | 底部「已配置 N 个账号」口径不变（按平台全量求和） | 行内计数改为「该站点 N 个账号」 |
| 「登录 / 添加账号」 | Qoder 每行各一个按钮，进入后站点锁定 | 其它平台仍是一个按钮、站点字段不存在 |
| 登录流程 | 站点下拉预置并置灰 | 会话仍按 `provider+method` 路由；`options.site` 来源于被锁定的值 |
| 手工添加 | 站点随锁定值提交 | 落到 `QODER_COOKIE` / `QODER_GLOBAL_COOKIE` 的规则不变（`envNames(options)`） |
| 删除 | 每行只列本站点账号 | 删除仍按 `displayName` 定位，逻辑不变 |
| 其它接口 / 后端探测 / 聚合 | 不变 | 仅 `ManagedAccountView` 多一个只读字段 |

## 7. 风险与备选方案

| 项 | 说明 | 处置 |
| --- | --- | --- |
| R1 站点改动后入口错位 | 用户在管理视图里想加另一站点却改不了下拉 | 每个站点行都有自己的入口；另提供「← 返回平台列表」 |
| R2 账号 `site` 缺失 | 老账号没写 `options.site`（默认按 cn 探测，见 `src/providers/qoder.ts:580`） | 归入「其他站点」行并显示原始值/「未指定」，仍可删除；**不会**被误算进国内版 |
| R3 `auto` 账号无法归类 | `auto` 是探测策略 | 归「其他站点」，不提供添加（登录也不支持 auto，见 `public/app.js:1198-1200`） |
| R4 `options` 泄露敏感值 | 若未来把凭证类字段声明成 option | 只下发显式声明为 `target: 'option'` 的键；`ManageFieldDescriptor` 已约定 option 为非敏感（`src/providers/base.ts:55-61`） |
| R5 上线前已有 `auto` 数据 | 行数变多 | 只在确有此类账号时出现一行，不影响常规使用 |
| R6 前后端版本错配 | 只重启前端没重启服务（或反之）时 `options` 缺失 | 前端检测到 `account.options === undefined` 就不拆行，退回改造前的单行表现，不会把账号归错 |
| 备选 A（否决）每站点一个独立 provider | 见 §1.3 | 与账号/缓存模型冲突 |
| 备选 B（否决）只在表单里加提示文案 | 不改结构 | 用户仍要自己看懂下拉选哪个；入口层面依旧分不清 |
| 备选 C（否决）前端写死「qoder 的两个站点」 | 快 | 违背「前端不认平台名」的既有约定（`public/app.js:1668`、`src/providers/index.ts:87-92`） |
